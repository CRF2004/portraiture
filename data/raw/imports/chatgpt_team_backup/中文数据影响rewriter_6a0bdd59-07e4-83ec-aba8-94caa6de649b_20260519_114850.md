## 🤖 Assistant (2026/5/19 11:48:50)

很可能不是“中文数据让模型变笨”，而是**你追加中文翻译后，训练目标被污染/分布被打乱了**。rewriter 这种任务特别敏感，因为它学的不是知识，而是“怎么改 generator 的输出”。一旦输入输出格式、修改粒度、语言风格不一致，效果很容易掉。

我按可能性从高到低说。

## 1. 中文翻译数据可能不是等价任务，而是变成了“翻译腔重写”

你原来的任务大概是：

> 输入 issue / critique / error list  
> 输出对 generator answer 的 targeted edit

但你追加“中文翻译”后，模型看到的可能变成：

> 英文 issue → 英文 revision  
> 中文 issue → 中文 revision  
> 或英文 answer + 中文 issue → 中文修改  
> 或中文 issue + 翻译后的 answer → 中文 revision

这会让模型混淆：它到底是在**修正内容**，还是在**翻译/改写语言**？

尤其是 rewriter，核心能力是：

> 保留原答案中正确部分，只局部修正 issue 指出的错误。

如果中文翻译数据里出现了更多“整段改写”“语言润色”“解释性扩写”，模型就会学偏，开始过度重写、变啰嗦、破坏原文结构。

## 2. 追加中文翻译可能引入了 label noise

翻译数据常见问题是：issue 翻译得还行，但 target rewrite 不一定和原英文 rewrite 完全等价。

比如英文 issue 是：

> The answer overstates the evidence.

翻译成中文可能是：

> 回答夸大了证据。

看起来没问题，但 target 如果被翻译成中文时，可能会改变措辞强度、医学术语、限定条件、语气，甚至让原本精确的修正变得模糊。

对普通聊天模型这点噪声不大；但对 rewriter 来说很致命。因为它要学的是“issue → 修改策略”的精细映射。翻译噪声会直接破坏这个映射。

## 3. 数据比例被改变，英文能力被中文样本“稀释”

如果你是“全英数据 + 对应中文翻译”，那等于每个样本变成两份。表面上数据量翻倍，但英文任务的占比下降了。

如果评测还是英文 rewriter，那么模型会被迫把容量分给中文模式，英文上的格式、风格、编辑习惯可能会退化。

尤其是小模型更明显。小模型容量有限，不一定能很好地同时学：

> 英文 issue → 英文 rewrite  
> 中文 issue → 中文 rewrite  
> 中英混合指令 → 保持原语言 rewrite

最后容易变成平均化策略：更保守、更泛化、更模板化，反而不如原来的纯英文版本。

## 🤖 Assistant (2026/5/19 11:49:21)

正常，而且**很常见**。你这个现象本质上不是“加中文一定会提升泛化”，而是：你把训练分布从“全英 rewriter”改成了“中英混合 rewriter”，但测试仍然是全英，于是模型可能在几个方面被干扰了。

核心原因大概有这几类：

### 1. 中文翻译数据改变了任务分布

原来模型学的是：

> English issue → English generator output → English edit

现在变成：

> English issue → English edit  
> Chinese translated issue → Chinese/translated edit

如果中文数据不是独立高质量样本，而是从英文翻译来的，它会引入新的表达模式、句法结构、错误类型和修改风格。模型容量有限时，它会把一部分能力用来适应中文模式，导致英文测试下降。

这在小模型或轻量 rewriter 上尤其明显。

---

### 2. 翻译数据可能不是“等价增强”，而是噪声增强

翻译后的 issue 很可能会改变原任务的细粒度含义。rewriter 对 issue 的依赖通常很强，比如：

- “too vague”
- “unsupported claim”
- “overstates the evidence”
- “missing safety disclaimer”
- “should be more concise”
- “tone is too definitive”

这些在中文里翻译后可能不再对应完全一样的修改行为。尤其是“评价标准”“错误类型”“修改意图”这类抽象信息，翻译很容易漂移。

所以你追加的中文数据不一定是在增强任务，而可能是在往训练集中加入 **label-preserving 不充分的 noisy augmentation**。

---

### 3. 输出风格可能被污染

rewriter 的目标不是简单回答问题，而是“改写 generator 输出”。它对格式、措辞、保守程度、句式都有强依赖。

中英混训后，模型可能学到一些不利于英文测试的模式，例如：

- 英文输出变得更像翻译腔；
- 修改幅度变大或变小；
- 更倾向解释 issue，而不是直接修改 output；
- 对 instruction 的跟随方式变弱；
- 在英文里混入中文式逻辑连接方式；
- 对原文 preservation 下降，改得太多。

这类问题不一定体现在 loss 上，但会明显伤害人工/LLM judge 评分。

---

### 4. 数据比例可能把英文能力“稀释”了

假设你原来有 10k 英文数据，现在追加 10k 中文翻译数据。看起来数据翻倍了，但对英文测试来说，有效英文训练比例从 100% 变成 50%。

如果模型本身不是强多语模型，或者训练步数/学习率没调整，就可能出现：

> 原本在英文 rewriter 任务上已经收敛，现在被继续训练到一个更偏多语但英文更差的位置。

这有点像 catastrophic forgetting / distribution shift，不奇怪。

---

### 5. tokenizer 和语言资源分配也会影响

中文 tokenization 通常更碎，训练时同样的样本数可能占用更多 token budget。结果是：

- 中文数据消耗了更多训练 token；
- 英文样本被看到的比例下降；
- 梯度更新更多来自中文模式；
- 英文任务的有效训练变少。

如果你是按 epoch 而不是按 token 控制训练，这个影响更明显。

## 我建议你先做几个诊断

最直接的不是看 overall score，而是切开看。

### A. 分语言测试

做三组 eval：

| 训练集 | 英文测试 | 中文测试 | 中英混合测试 |
|---|---:|---:|---:|
| English only | 高 | 低/未知 | 中 |
| English + Chinese translated | 下降？ | 上升？ | 可能上升 |

如果英文下降、中文上升，那就是典型 trade-off，不是 bug。

如果英文和中文都下降，那说明中文翻译数据质量或训练设置有问题。

---

### C. 检查翻译数据格式是否完全一致

这个很重要。中英数据里是否有这些不一致：

- 英文样本输出是纯 rewrite，中文样本输出带解释；
- 中文 issue 是翻译后的，但 generator output 还是英文；
- 中文输入中字段名被翻译了，比如 `issue` 变成“问题”；
- system/user/assistant 模板不一致；
- 中文样本里有“修改如下”“以下是修改后版本”这类前缀；
- 翻译时把 `generator output` 也翻译了，但测试时输出要求英文。

只要有一点格式漂移，rewriter 很容易被带歪。

## 怎么改比较稳

我会按这个顺序试：

### 方案 1：英文测试为主，就不要直接 1:1 追加中文

把中文比例降下来，例如：

| 英文 | 中文 |
|---:|---:|
| 90% | 10% |
| 80% | 20% |
| 70% | 30% |

不要一上来 50/50。你现在测试都是英文，那中文只是辅助，不能喧宾夺主。

---

### 方案 2：混训后再用英文做一轮短暂 continued finetune

流程：

1. English + Chinese 混训，获得多语能力；
2. 再用 English-only 小学习率训练 0.2–0.5 epoch；
3. 用英文 dev set early stopping。

这通常能把英文风格拉回来。

---

### 方案 3：把中文作为 instruction 理解，不要让输出语言漂移

如果你的最终测试是英文，可以设计成：

> Chinese issue + English generator output → English rewrite

而不是：

> Chinese issue + Chinese generator output → Chinese rewrite

这样模型学的是“能理解中文 issue，但输出仍保持英文”。否则它会学成多语 rewriter，而不是英文 rewriter。

---

### 方案 4：不要用机器翻译全量扩增，优先翻译 issue 类型标签

如果 issue 是自然语言描述，可以考虑把它结构化：

```json
{
  "issue_type": "unsupported_claim",
  "severity": "major",
  "instruction": "Revise the answer to avoid unsupported causal claims."
}
```

中文数据可以只增强 issue 理解，但保持统一的英文修订目标。对 rewriter 来说，结构化比翻译自然语言更稳定。

---

### 方案 5：训练时加语言控制字段

比如：

```text
Output language: English.
Task: Rewrite the generator output according to the issue.
Issue: ...
Generator output: ...
```

中英混训时尤其要加，不然模型会自己猜输出语言。

## 我的判断

你的结果**完全正常**。更准确地说，它说明：

> 中文翻译数据没有在当前测试分布上提供有效增益，反而引入了分布偏移和修改风格漂移。

如果你的目标是“英文 rewriter 表现最好”，那 English-only 或 “mixed + English replay/finetune” 大概率更好。

如果你的目标是“中英 issue 都能处理，输出英文修改”，那应该重构数据，而不是简单把英文数据翻译后追加进去。最稳的是：**保持输出格式和输出语言不变，只扩展 issue 语言多样性，并控制中文比例**。
