这不是“微调一定会变强”的反例，而是很典型的 SFT 把模型的原生指令跟随能力覆盖/扰乱了。

我的判断：报告里“LoRA rank=16 太弱”这个结论不够稳。更像是下面几个问题叠加了：

### 1. 训练目标在教模型“续写”，不是强约束“评估”

SFT 本质是 next-token prediction。你的 prompt 最后是：

**Response to Evaluate**: {被评估的AI回答全文}


然后 assistant target 立刻开始：

[
  "The response ..."
]


如果边界不够硬，模型很容易把 {被评估的AI回答} 当成正在继续生成的上下文，尤其它本来就是医学回答文本。微调后出现 52–56% “纯续写被评估答案”，正好说明模型在这个边界上学歪了。报告里的表格显示：base 没有纯续写，微调后纯续写直接涨到 52–56%，平均输出长度也从 4,324 chars 膨胀到 10,000+ chars。fileciteturn2file0

### 2. base 已经会做 checker，微调反而破坏了它

你这份结果里，base 其实 100% 都能执行 checker 任务，只是 99% 前面有 prose，需要解析端提取 JSON。也就是说，base 的问题主要是“格式不够干净”，不是“不会遵循任务”。微调之后虽然“直接 [ 开头”从 1% 提到 34%，但代价是过半样本完全不可用。fileciteturn2file0

这说明你优化错了主要矛盾：你本来只需要 输出格式控制/解析增强，却用 SFT 去改模型行为，结果把原本的任务理解能力也动到了。

### 3. “rank 太弱”不是最可能主因

如果 LoRA 太弱，通常表现应该是“没怎么改变 base”，而不是把纯续写率从 0% 打到 50%+。这个退化幅度说明 adapter 已经有足够能力干扰原模型。

我更怀疑这些点：

1. label mask 可能有问题：确认训练 loss 是否只打在 assistant output 上，而不是把 user prompt/input 也算进 loss。
2. EOS / <end_of_turn> stop 设置可能有问题：微调后平均输出变长 2.5 倍，像是模型没学好停止，或推理时没有把 Gemma 的 turn stop token 放进 eos_token_id/stop list。
3. 样本边界太弱：Response to Evaluate 后面没有强分隔符，也没有在 answer 结束后明确写“END OF RESPONSE”。
4. 学习率/epoch 对小数据偏猛：3k–6k 条、3 epoch、all-linear LoRA、lr=5e-5，对一个已经 instruction-tuned 的 27B 模型来说，足够把某些行为覆盖掉。
5. 评估目标和训练目标不一致：你真正要的是“可解析 JSON”，但训练在强行改变整个生成分布。

### 我会按这个顺序排查

第一，dump 一条训练样本的最终 token 和 labels，确认：

<start_of_turn>user
...完整 prompt...
<end_of_turn>
<start_of_turn>model
[
  ...
]
<end_of_turn>


并且 user 部分 labels 全是 -100，assistant 的 [、JSON 内容、<end_of_turn> 都有 loss。

第二，检查每条样本 token 长度。max_length=8192，而 instruction 本身就 4146 chars，再加完整对话和被评估答案，很可能有样本被截断。重点看：有没有 target 开头、target 结尾、<end_of_turn> 被截断。

第三，把 prompt 改成强边界格式：

**Response to Evaluate**:
<<<BEGIN_RESPONSE_TO_EVALUATE>>>
{answer}
<<<END_RESPONSE_TO_EVALUATE>>>

Now produce ONLY the checker assessment.
The first character of your answer must be `[`.
Do not continue the response above.
Return a valid JSON array of strings.


训练和推理都用这个格式。

第四，推理时加 stop：

eos_token_id = [
    tokenizer.eos_token_id,
    tokenizer.convert_tokens_to_ids("<end_of_turn>")
]


同时把 max_new_tokens 降到比如 512 或 768。checker 不应该生成 10k chars。

第五，先别继续扩大数据。用 200 条样本做 sanity check：过拟合训练集，看训练集上是否 100% 以 [ 开头、是否 0% 续写。如果训练集都不稳，问题在模板/label/stop；不是数据量。

### 结论

这次不是“微调让模型更笨了”，而是 微调把一个本来会遵循 checker 指令的模型，推向了医学回答续写分布。当前最实用方案确实是：先用无微调 base + parse_json_maybe() 提取 JSON；如果还要微调，只做一个非常小的格式校正实验，并先把 label mask、截断、stop token、边界 sentinel 查清楚。

我对这个报告的判断：“LoRA rank=16 太弱”不是最可信的主因。更像是下面两类问题之一，或者两者叠加：

1. 推理端解码/截断有问题，导致把 prompt 尾巴当成模型输出
2. 训练/推理 prompt 边界不够硬，微调后模型学坏成“续写 Response to Evaluate”模式

你给的现象非常典型：base 模型 100% 能做 checker，只是 99% 前面带一段可解析前缀；微调后虽然 34% 直接 JSON，但 52–56% 变成纯续写，而且输出长度暴涨到约 10k chars。这个不像“rank 太小导致学不会”，反而像 SFT 把原本会遵循指令的模型推离了稳定区间。报告里这些数据支持这个判断：base 的纯续写率是 0%，微调后纯续写率直接到 52–56%，平均输出长度也从 4,324 chars 涨到 10,290–10,703 chars。fileciteturn2file0

最可疑的一点是：base 样例前缀是 g., organ transplant recipients...，这不像模型自然生成的“prose”，更像是 被评估回答的尾巴残留在 decoded output 里。微调样例里的 skin tag but is actually... 也很像同一类问题：模型输出里可能混进了 Response to Evaluate 的内容，或者模型确实从这个位置开始续写。你需要先把这两种情况分开，否则会误判成模型能力退化。

我会按优先级这样查：

### 1. 先排除解码切片 bug

在推理代码里不要看最终 parse 后的字符串，直接打印 new tokens：

outputs = model.generate(
    **inputs,
    max_new_tokens=2048,
    do_sample=False,
    eos_token_id=tokenizer.eos_token_id,
    pad_token_id=tokenizer.pad_token_id,
)

new_tokens = outputs[:, inputs["input_ids"].shape[1]:]
print(tokenizer.batch_decode(new_tokens, skip_special_tokens=False)[0][:1000])
print(tokenizer.convert_ids_to_tokens(new_tokens[0][:30]))


如果 new_tokens 第一批 token 其实是 [ 或 \n[，那模型没坏，是你后处理/截断把 prompt 尾巴带进来了。

如果 new_tokens 第一批 token 真的是 skin, tag, but, is 这种待评估回答的续写，那才是模型真的学坏了。

另外 batch 推理时确认：

tokenizer.padding_side = "left"
tokenizer.pad_token = tokenizer.eos_token


decoder-only 模型右 padding 批量生成很容易出怪结果。先用 batch_size=1 复现实验，能快速判断是不是 padding/batching 问题。

### 2. 检查训练 labels，尤其是 user prompt 是否被 mask 掉

这是我最想看的。你要确认训练时只有 assistant 的 JSON output 参与 loss，user 侧的 instruction + input + Response to Evaluate 全部是 -100。

抽一条训练样本，打印 token、label：

for tid, lab in zip(input_ids, labels):
    tok = tokenizer.decode([tid])
    if lab != -100:
        print(repr(tok), lab)


正确现象应该是：第一个非 -100 token 基本就是 [ 或换行后 [。
如果 Response to Evaluate 后面的医学回答也参与了 loss，那模型被训练成续写医学回答就完全合理了。

### 3. prompt 边界确实偏弱

你现在的输入最后是：

**Response to Evaluate**: {被评估的AI回答全文}


然后直接 <end_of_turn><start_of_turn>model。

这对 base 还能靠 instruction 扛住；但 SFT 后模型可能更依赖局部上下文，最后看到的是一大段医学回答，于是进入“继续写医学回答”的模式。建议改成强边界：

**Response to Evaluate**:
<response_to_evaluate>
{answer}
</response_to_evaluate>

Now produce the assessment.
Return ONLY a JSON array of strings.
The first character of your response must be `[`.


更狠一点：推理时给 assistant 预填充 [，让模型只能补 JSON 内容：

<start_of_turn>model
[


然后解析时把 [ 拼回去。这通常比 SFT 更有效。

### 4. 微调强度不是“太弱”，更可能是“太猛/方向错”

rank=16 + all-linear + lr=5e-5 + 3 epochs + 3k/6k 样本 对 27B LoRA 来说并不弱。all-linear 会改很多模块，3 个 epoch 在小而单一的数据集上足够把模型的原生指令跟随扰乱。你看到的是“直接 JSON 提升，但大面积续写崩掉”，这更像过拟合/格式边界学习错误，而不是容量不足。

如果确认不是解码 bug，我会改成：

--learning_rate 1e-5 或 2e-5
--num_train_epochs 1
--target_modules q_proj,k_proj,v_proj,o_proj 或 q_proj,v_proj,o_proj
--lora_rank 8 或 16


并且训练数据里加入更多“强边界 + only JSON”的格式，而不是只靠长 instruction。
