# 一、为什么会有模糊性的本质原因（为什么你在 MIMIC 里看不出“为什么做某项检查”）
1. EHR 不是为因果问答设计的记录系统：很多关键“决策原因”只存在于医生脑里或纸面记忆里，EHR 只记录了动作（下了检查单、做了操作、时间、结果），但不总记录“为什么”（临床怀疑、规则、床位/科室、值班医师偏好等）。这在文献里被反复指出——用 EHR 做因果发现困难且容易被未观测混杂偏倚。citeturn0search0turn0search3

2. 选择偏倚与未观测混杂（selection & unobserved confounding）：做或不做某检查往往与患者严重度、检验可得性、科室流程或医生偏好相关，这些因子可能没有完备记录。直接把“观察到做了检查”解释为“由先前某些体征导致”的因果链，容易误判。citeturn0search3turn0search14

3. 时间与事件稀疏、异构：不同病人在不同时间点做不同动作，事件集合不一致（有人做 ECG，有人没做）。传统时序因果模型（如 DBN、传统 Granger）对这种异构稀疏事件支持不好。

# 二、两条可行策略（优劣比较）

- 优点：能快速把真实世界的常见路径可视化并量化；对构建决策支持和发现异常路径非常有用。Process mining 在医疗流程可视化上已有成熟研究与工具。citeturn0search7turn0search1
- 局限：这只是相关，不能保证“先兆事件 → 决策”是因果关系。

## B. 做因果发现 / 因果识别（针对关键决策做深挖）
- 做法：对你关心的若干关键决策（例如：为何在 ICU 某类病人要做 echo）构建因果图（结合临床专家），用 DoWhy /因果发现算法/IV/倾向评分 /自然实验等做识别与估计。也可用 clinician preference 作为工具变量（clinician preference IV），或用选取规则做准实验仿真。文献中很多做法说明：EHR 上做因果需要 clinician-in-loop + 强假设。citeturn0search26turn0search21

- 可以扩展 tuple 表示 (状态集合 → 决策集合)

- 输出：流程图/树，边可以标注：
- 频次：多少病例中发生过这个转移
- 概率/支持度：这个转移占总病例的比例

关键概念：

- 节点 = 活动/事件（你可以把它映射为“状态节点”或“决策节点”）
- 边 = 直接转移 / 可选窗口转移
- 可以计算 直接跟随（Directly-Follows）或近邻随访（k-length window）
- 可以处理非严格线性序列，也能统计多条病例中出现的模式

# 2️⃣ 多对一/多对多支持情况

## 多对一

- 定义：多个前置事件 → 一个后置事件（决策）
- PM4Py 默认建 Directly-Follows Graph (DFG) 时是基于相邻事件，看起来像“一对一”
- 扩展支持多对一：
- 使用 窗口技术 或 Heuristics Miner / Inductive Miner：
- 给每个事件定义前置窗口（例如前 6 小时或前 N 个事件）
- 把窗口内的所有前置事件作为触发集合
- 统计所有病例中出现这个集合 → 后置事件的频次/概率
- 结果就是多对一边（多个状态指向一个决策）

> 核心就是把事件组合看作触发集合，而不是只考虑直接前一个事件。

## 多对多

- 类似多对一，只是后置事件也是集合（一个状态集合可能触发多个决策）
- PM4Py 可以通过 “parallel/branching” 或 Process Tree 表示分叉，统计所有可能的后续分支频次

---

# 3️⃣ 非相邻事件的处理

- 默认 DFG 只统计直接相邻事件
- 支持非相邻事件的方法：
1. 事件窗口（sliding window / temporal threshold）
- 对每个决策事件，定义一个时间窗口（如前 6 小时）
- 所有窗口内事件都统计为候选前置事件
2. 序列模式挖掘结合 PM4Py
- 可以先用 PrefixSpan / SPADE 找高频序列模式，再用 PM4Py 可视化成流程树

> 这就允许你捕捉“非相邻触发、多对一、多对多”的模式，同时还能生成决策森林可视化。

- 呼吸频率每 5–15 分钟
- SpO2 每分钟
- 神经评分每小时
- 输入输出每小时

这些都不是“临床事件（clinical events）”，只是：

- 一段时间内状态大致稳定的采样点
- 并不代表状态真正“变化”了
- 甚至不代表任何临床意义
- 不会指导任何临床决策

所以：

> chart events 大部分应该被压缩为“状态段（state intervals）”而不是一个个节点。

- 高频 nodes（比如 HR_normal）因频繁出现会 dominate

- 新影像
- 急变（tachycardia, hypoxia）
- 疑似感染
- 血流动力学改变
- 医嘱、药物变化

驱动。

- 每 15 分钟一次的心率监测

# ✔ 那应该怎么处理 chart events？

# 🎯 关键步骤：时间抽象（Temporal Abstraction）

## 1. 合并相邻、相同状态 —— 按状态段压缩

示例：

08:00 HR_normal
08:05 HR_normal
08:10 HR_normal
08:15 HR_normal
→ 合并为一条：
08:00–08:15 HR_normal


减少 ≥95% 的节点。

---

## 2. 只保留“变化点”（state change points）

例如：

HR_normal → HR_tachy (变化点)
RR_normal → RR_high (变化点)
Temp_normal → fever (变化点)


无变化的连续记录全部丢弃。

这是最核心的操作，会让 18,000 条变成几十条到几百条。

---

## 3. 时间粒度下采样（可选）

保留：

- 每小时一个摘要
- 或每 30 分钟一个统计结果（min/max/median）

适用于特别密集的 ICU 信号。

---

## 4. 事件过滤（过滤无信息量事件）

例如：

- Vital_normal 这种 baseline 事件可以只保留“第一次出现”
- I/O 记录每小时一次，不作为状态节点
- 护理 routine（monitor, flush, check tube）可过滤掉
