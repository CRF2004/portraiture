# 二、核心模块设计

---

## 1️⃣ Token Profiler（最关键）

👉 这是你系统的“感知层”，没有它就无法自动 fork

### 功能
- 统计：
- 每轮 prompt token
- 每个 tool / MCP server token
- 每个 skill token
- 实时 context 占用率
- breakdown：

{
  "total": 120000,
  "messages": 20000,
  "tools": 40000,
  "mcp_servers": {
    "github": 12000,
    "notion": 8000
  },
  "skills": 15000
}


---

### 实现方式（关键点）

#### 方法1：hook Claude Code 请求
- 拦截：
- system prompt
- messages
- tool schemas
- 用 tokenizer 计算（如 tiktoken / anthropic tokenizer）

#### 方法2：MCP wrapping
- 给每个 MCP server 加 wrapper
- 统计其 schema + 返回内容 token

---

### 输出指标（用于 fork 判断）

context_ratio = used_tokens / max_tokens

risk_level:
    <0.6 → safe
    0.6–0.8 → warning
    >0.8 → critical


---

## 2️⃣ Context Manager（上下文切片）

👉 控制“传什么给模型”

### 核心能力

#### ✅ context 分层

L1: system prompt
L2: 当前任务
L3: 当前文件
L4: 相关依赖摘要
L5: 历史对话（可裁剪）
L6: tools / MCP schemas


---

#### ✅ 动态裁剪策略

当 token 超标：

1. 删除旧对话
2. 压缩历史（summarize）
3. 移除不必要 tools
4. 精简 MCP schema

---

#### ✅ context snapshot

每个 session 保存：

{
  "task": "...",
  "files": ["a.py", "b.py"],
  "summary": "...",
  "state": {...}
}


👉 用于 fork 迁移

---

## 3️⃣ Fork Manager（核心创新点）

👉 你这个项目最有价值的部分

---

### 🔥 fork 触发策略

#### 条件（可组合）：

if (
    context_ratio > 0.8
    or response_latency > threshold
    or hallucination_risk ↑
):
    trigger_fork()


---

### 🔥 fork 执行流程

[旧 session]
     ↓
1. summarize context
     ↓
2. 提取关键状态
     ↓
3. 创建新 session
     ↓
4. 注入精简 context
     ↓
5. 继续任务


---

### 🔥 fork 数据结构

{
  "parent_session": "A",
  "child_session": "B",
  "summary": "...",
  "carried_context": [
    "task",
    "fileA.py",
    "api_spec"
  ]
}

| 类型 | 用途 |
