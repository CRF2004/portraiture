## 推荐主题

**面向心血管患者的住院期健康轨迹建模与康复风险预警系统**

## 核心思想

不是只预测一次“是否死亡/是否患病”，而是把每个患者按时间切成多个状态点，例如：

**入院第 1 天 → 第 2 天 → 第 3 天 → 出院前**

每一天提取患者的生命体征、实验室检查、诊断、用药等指标，形成一条健康状态轨迹。然后系统分析：

1. 患者健康状态是在好转、稳定还是恶化；
2. 不同患者可以被聚成哪些轨迹类型；
3. 哪些患者属于高危康复风险人群；
4. 哪些指标导致风险升高；
5. 医生或随访人员应该优先关注哪些患者。

这样比普通分类高级很多，而且仍然可以稳妥实现。

## 可以做的数据分析功能

建议做 4 个模块：

### 1. 患者健康轨迹构建

从 MIMIC-IV 中抽取心血管相关患者，比如心衰、心梗、冠心病、高血压等患者。

按天聚合数据：

| 时间点 | 心率 | 血压 | 血氧 | 体温 | 白细胞 | 肌酐 | 血红蛋白 | 诊断 | 用药 | 状态评分 |
|---|---:|---:|---:|---:|---:|---:|---:|---|---|---:|
| Day 1 | ... | ... | ... | ... | ... | ... | ... | HF | ... | 72 |
| Day 2 | ... | ... | ... | ... | ... | ... | ... | HF | ... | 68 |
| Day 3 | ... | ... | ... | ... | ... | ... | ... | HF | ... | 55 |

然后定义：

- 状态评分下降：病情好转；
- 状态评分上升：病情恶化；
- 波动大：状态不稳定；
- 出院前仍高风险：康复风险高。

这个模块很适合写“轨迹建模”。

### 2. 轨迹类型聚类

可以用：

- K-Means；
- 层次聚类；
- DTW + 聚类；
- 或者更稳一点：先提取轨迹统计特征，再做 K-Means。

比如把患者分成：

| 轨迹类型 | 特征 | 解释 |
|---|---|---|
| 快速恢复型 | 风险评分持续下降 | 康复预后较好 |
| 稳定高危型 | 风险评分长期偏高 | 需要重点随访 |
| 波动恶化型 | 风险评分反复升高 | 可能存在并发症风险 |
| 低危稳定型 | 入院后持续低风险 | 常规管理即可 |

这个非常适合界面展示。

### 3. 康复风险预测

预测患者出院后是否需要重点随访。由于 MIMIC 没有真实院后康复标签，可以用替代标签，例如：

- 住院死亡；
- ICU 内死亡；
- 住院时间过长；
- 出院前高风险；
- 24/48 小时内病情恶化；
- 再次进入 ICU；
- 出院去向为非正常回家。

其中最稳的是：

> **预测患者未来 24/48 小时是否发生健康状态恶化**

这不需要伪造“院后康复数据”，而且完全基于 MIMIC-IV 的时间序列数据。

### 4. 影响因素解释

用 Random Forest / XGBoost / Logistic Regression 做预测，再用特征重要性解释：

- 心率升高；
- 血氧下降；
- 肌酐异常；
- 白细胞升高；
- 年龄较高；
- 合并症数量多；
- 住院前几天状态波动大。

这个部分很容易写进报告，也符合课程设计“数据分析结果”的要求。

**任务 2：轨迹模式聚类**

把患者轨迹变成特征，例如：

## 可以实现的分析方法

不需要复杂到 Transformer。课程设计可以用这些方法，足够了：

### 1. 轨迹标准化

不同患者时间长度不同，所以先统一成时间窗口。

例如：

前 24 小时，每 4 小时一个时间片。  
每个时间片统计平均心率、平均血压、最低血氧、最高体温等。  
最后得到一个固定长度的轨迹向量。

比如一个患者可以表示成：

```text
[HR_0-4h, HR_4-8h, ..., SpO2_0-4h, SpO2_4-8h, ..., Creatinine_0-24h]
```

### 2. 相似轨迹检索

可以实现三种相似度：

**欧氏距离**：最简单，适合课程设计。  
**余弦相似度**：适合比较趋势方向。  
**DTW 动态时间规整**：更有亮点，适合处理时间错位的轨迹。

报告里可以写：

> 系统采用标准化后的多变量时间序列作为患者轨迹表示，并通过相似度计算从历史轨迹库中检索 Top-K 相似患者。

### 3. 相似患者后续趋势分析

检索到 Top-10 或 Top-20 相似患者后，不是只给列表，而是分析他们后续走势。

例如展示：

相似患者后续 24h 平均心率趋势。  
相似患者后续 24h 血氧变化趋势。  
相似患者中有多少比例进入高危状态。  
相似患者平均 ICU 停留时间。  
相似患者主要结局分布。

这就是你的“下一时间步甚至若干时间步可能健康情况”。

### 4. 轨迹类型归纳

可以再加一个聚类模块：

稳定型轨迹。  
持续恶化型轨迹。  
波动恢复型轨迹。  
循环/呼吸不稳定型轨迹。  
肾功能恶化型轨迹。

然后系统告诉用户：

## 七、相似度计算方法

先做一个稳妥版本：

### 方案 1：标准化向量 + 欧氏距离

把前 24h 轨迹压缩成特征向量：

```text
每个指标的均值、最大值、最小值、最后一次值、变化斜率、波动幅度
```

然后标准化：

```text
z-score 标准化
```

计算距离：

```text
distance = 欧氏距离
similarity = 1 / (1 + distance)
```

优点：实现简单，报告好解释。

### 方案 2：加入治疗上下文过滤

先要求候选患者满足：

```text
循环支持相同或相近
呼吸支持相同或相近
液体管理相同或相近
```

再计算轨迹相似度。

这个是你的创新点之一。

### 方案 3：可选增强，DTW 轨迹距离

如果后面时间够，可以加一个动态时间规整 DTW，用来比较时间序列形状。

但第一版不要依赖 DTW，避免实现不稳。

## 八、后续趋势怎么定义

系统检索 Top-K 相似患者后，需要给出“后续趋势参考”。

可以定义三个趋势类型：

```text
改善：24–48h 综合健康评分下降，或关键异常指标改善
稳定：综合评分变化不大
恶化：综合评分上升，或关键异常指标明显恶化
```

为了简单，可以构造一个健康异常评分：

```text
health_score =
心率异常程度
+ 血压异常程度
+ 血氧异常程度
+ 呼吸频率异常程度
+ 肌酐异常程度
+ 白细胞异常程度
+ 乳酸异常程度
```

然后比较：

```text
score_0_24h 与 score_24_48h
```

输出：

```text
相似患者中：
50% 稳定
30% 改善
20% 恶化
```

这就能形成“趋势参考”。

## 1. 抽主队列

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS course_ihd_icu48 AS
WITH ihd_adm AS (
    SELECT
        subject_id,
        hadm_id,
        STRING_AGG(DISTINCT SUBSTRING(icd_code FROM 1 FOR 3), ',') AS ihd_icd_prefixes
    FROM mimiciv_hosp.diagnoses_icd
    WHERE
        (icd_version = 9  AND SUBSTRING(icd_code FROM 1 FOR 3) BETWEEN '410' AND '414')
        OR
        (icd_version = 10 AND SUBSTRING(icd_code FROM 1 FOR 3) BETWEEN 'I20' AND 'I25')
    GROUP BY subject_id, hadm_id
),
icu_base AS (
    SELECT
        i.subject_id,
        i.hadm_id,
        i.stay_id,
        i.intime,
        i.outtime,
        EXTRACT(EPOCH FROM (i.outtime - i.intime)) / 3600.0 AS icu_hours
    FROM mimiciv_icu.icustays i
    INNER JOIN ihd_adm c
        ON i.subject_id = c.subject_id
       AND i.hadm_id = c.hadm_id
)
SELECT
    b.subject_id,
    b.hadm_id,
    b.stay_id,
    p.gender,
    p.anchor_age,
    a.admittime,
    a.dischtime,
    b.intime,
    b.outtime,
    b.icu_hours,
    a.hospital_expire_flag,
    EXTRACT(EPOCH FROM (a.dischtime - a.admittime)) / 3600.0 AS los_hospital_hours,
    c.ihd_icd_prefixes
FROM icu_base b
JOIN ihd_adm c
    ON b.subject_id = c.subject_id
   AND b.hadm_id = c.hadm_id
LEFT JOIN mimiciv_hosp.patients p
    ON b.subject_id = p.subject_id
LEFT JOIN mimiciv_hosp.admissions a
    ON b.hadm_id = a.hadm_id
WHERE b.icu_hours >= 48;
```

常用 itemid 先按下面这组，最好再用 `d_items` 核验一次：

SQL：

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS course_vitals_4h_bins AS
WITH vitals_raw AS (
    SELECT
        c.stay_id,
        CASE
            WHEN ce.itemid = 220045 THEN 'heart_rate'
            WHEN ce.itemid IN (220050, 220179) THEN 'sbp'
            WHEN ce.itemid IN (220052, 220181) THEN 'map'
            WHEN ce.itemid = 220210 THEN 'resp_rate'
            WHEN ce.itemid = 220277 THEN 'spo2'
            WHEN ce.itemid IN (223761, 223762) THEN 'temperature'
        END AS variable,
        FLOOR(EXTRACT(EPOCH FROM (ce.charttime - c.intime)) / 3600.0 / 4.0)::int AS bin_id,
        CASE
            WHEN ce.itemid = 223761 THEN (ce.valuenum - 32.0) * 5.0 / 9.0
            ELSE ce.valuenum
        END AS value
    FROM mimiciv_icu.chartevents ce
    JOIN course_ihd_icu48 c
        ON ce.stay_id = c.stay_id
    WHERE ce.charttime >= c.intime
      AND ce.charttime <  c.intime + INTERVAL '48 hours'
      AND ce.valuenum IS NOT NULL
      AND ce.itemid IN (
          220045,
          220050, 220179,
          220052, 220181,
          220210,
          220277,
          223761, 223762
      )
),
vitals_clean AS (
    SELECT *
    FROM vitals_raw
    WHERE
        bin_id BETWEEN 0 AND 11
        AND (
            (variable = 'heart_rate'  AND value BETWEEN 20 AND 300)
            OR (variable = 'sbp'       AND value BETWEEN 40 AND 300)
            OR (variable = 'map'       AND value BETWEEN 20 AND 200)
            OR (variable = 'resp_rate' AND value BETWEEN 1  AND 80)
            OR (variable = 'spo2'      AND value BETWEEN 50 AND 100)
            OR (variable = 'temperature' AND value BETWEEN 25 AND 45)
        )
)
SELECT
    stay_id,
    variable,
    bin_id,
    bin_id * 4 AS bin_start_hour,
    (bin_id + 1) * 4 AS bin_end_hour,
    AVG(value) AS mean_value,
    MIN(value) AS min_value,
    MAX(value) AS max_value,
    STDDEV(value) AS std_value,
    COUNT(*) AS n_obs
FROM vitals_clean
GROUP BY stay_id, variable, bin_id;
```

## 3. 抽实验室检查 0–24h / 24–48h

常用 lab itemid：

```text
bun: 51006
creatinine: 50912
hemoglobin: 51222
potassium: 50971
sodium: 50983

```

SQL：

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS course_labs_24h_windows AS
WITH labs_raw AS (
    SELECT
        c.stay_id,
        CASE
            WHEN le.itemid = 51006 THEN 'bun'
            WHEN le.itemid = 50912 THEN 'creatinine'
            WHEN le.itemid = 51222 THEN 'hemoglobin'
            WHEN le.itemid = 50971 THEN 'potassium'
            WHEN le.itemid = 50983 THEN 'sodium'
            WHEN le.itemid IN (51300, 51301) THEN 'wbc'
        END AS variable,
        CASE
            WHEN le.charttime >= c.intime
             AND le.charttime <  c.intime + INTERVAL '24 hours'
                THEN '0_24h'
            WHEN le.charttime >= c.intime + INTERVAL '24 hours'
             AND le.charttime <  c.intime + INTERVAL '48 hours'
                THEN '24_48h'
        END AS window,
        le.charttime,
        le.valuenum AS value
    FROM mimiciv_hosp.labevents le
    JOIN course_ihd_icu48 c
        ON le.subject_id = c.subject_id
       AND le.hadm_id = c.hadm_id
    WHERE le.charttime >= c.intime
      AND le.charttime <  c.intime + INTERVAL '48 hours'
      AND le.valuenum IS NOT NULL
      AND le.itemid IN (51006, 50912, 51222, 50971, 50983, 51300, 51301)
),
labs_clean AS (
    SELECT *
    FROM labs_raw
    WHERE window IS NOT NULL
      AND (
          (variable = 'bun'        AND value BETWEEN 1 AND 300)
          OR (variable = 'creatinine' AND value BETWEEN 0.1 AND 30)
          OR (variable = 'hemoglobin' AND value BETWEEN 3 AND 25)
          OR (variable = 'potassium'  AND value BETWEEN 1 AND 10)
          OR (variable = 'sodium'     AND value BETWEEN 100 AND 180)
          OR (variable = 'wbc'        AND value BETWEEN 0.1 AND 300)
      )
),
ranked AS (
    SELECT
        *,
        FIRST_VALUE(value) OVER (
            PARTITION BY stay_id, variable, window
            ORDER BY charttime
        ) AS first_value,
        FIRST_VALUE(value) OVER (
            PARTITION BY stay_id, variable, window
            ORDER BY charttime DESC
        ) AS last_value
    FROM labs_clean
)
SELECT
    stay_id,
    variable,
    window,
    AVG(value) AS mean_value,
    MIN(first_value) AS first_value,
    MIN(last_value) AS last_value,
    MIN(value) AS min_value,
    MAX(value) AS max_value,
    MIN(last_value) - MIN(first_value) AS delta_value,
    COUNT(*) AS n_obs
FROM ranked
GROUP BY stay_id, variable, window;
```

),

    SELECT
        c.stay_id,
        SUM(oe.value) AS fluid_output_ml_0_24h
    FROM course_ihd_icu48 c
    LEFT JOIN mimiciv_icu.outputevents oe
        ON oe.stay_id = c.stay_id
       AND oe.charttime >= c.intime
       AND oe.charttime <  c.intime + INTERVAL '24 hours'
       AND oe.value IS NOT NULL
    GROUP BY c.stay_id
)
SELECT
    c.stay_id,
    COALESCE(i.fluid_input_ml_0_24h, 0) AS fluid_input_ml_0_24h,
    COALESCE(o.fluid_output_ml_0_24h, 0) AS fluid_output_ml_0_24h,
    COALESCE(i.fluid_input_ml_0_24h, 0) - COALESCE(o.fluid_output_ml_0_24h, 0) AS net_fluid_ml_0_24h
FROM course_ihd_icu48 c
LEFT JOIN input_ml i ON c.stay_id = i.stay_id
LEFT JOIN output_ml o ON c.stay_id = o.stay_id;

# 五、趋势标签怎么做

```python
def trend_label(delta, improve_direction="down", threshold=0.05):
    if pd.isna(delta):
        return "unknown"
    if abs(delta) <= threshold:
        return "stable"
    if improve_direction == "down":
        return "improved" if delta < 0 else "worsened"
    else:
        return "improved" if delta > 0 else "worsened"
```

更稳的做法是只给**描述性趋势**，不要强行判断临床改善：

## 趋势标签怎么定义

后续 24h 的趋势不建议做得太医学复杂。可以按核心指标变化分成三类：

```text
改善
稳定
恶化
```

比如对每个患者计算 24–48h 相比 0–24h 的变化：

```text
MAP 下降明显、SpO2 下降、HR 升高、肌酐升高、BUN 升高、WBC 升高 → 偏恶化
MAP 稳定、SpO2 稳定、HR 下降或稳定、肾功能指标稳定 → 偏稳定/改善
```

课程设计里可以先用一个简单的综合趋势评分：

```text
trend_score = 
  +1 × 不利变化指标数量
  -1 × 有利变化指标数量
```

然后：

```text
trend_score ≥ 2    → 恶化
-1 ≤ trend_score < 2 → 稳定
trend_score ≤ -2   → 改善
```

这个规则不一定临床完美，但课程设计足够用，而且可解释。

## 2. 主题定位

本课程设计不采用传统的“训练模型预测死亡率”路线，而是设计一个更具系统感和应用感的**患者健康轨迹检索系统**。

系统面向缺血性心脏病 ICU 患者，基于 MIMIC-IV 数据构建历史患者健康轨迹库。用户选择一个目标患者后，系统根据其 ICU 入科后前 24 小时的生命体征、实验室检查和治疗上下文，在历史患者轨迹库中检索相似患者，并统计这些相似患者在后续 24 小时的健康变化，为医护人员提供相似病例参考和趋势分析支持。

核心思想：

```text
目标患者前 24h 健康轨迹
        ↓
匹配治疗上下文相近的历史患者
        ↓
计算轨迹相似度
        ↓
返回 Top-K 相似患者
        ↓
统计相似患者 24–48h 后续趋势
        ↓
形成趋势参考与可视化结果
```

系统定位必须注意：

> 本系统不是临床诊断系统，也不直接给出治疗方案，而是一个基于历史数据的相似病例检索与趋势参考工具。

这句话很重要，可以避免报告中被质疑“医学预测不可靠”或“系统越界”。

## 7. 核心算法设计

### 7.1 轨迹特征构建

对每个 stay_id，在 0–24h 内对 12 个变量提取统计特征。

每个变量特征：

```text
mean: 平均水平
min: 最低值
max: 最高值
std: 波动程度
last: 窗口末次值
slope: 变化趋势
```

slope 可以用简单线性回归斜率计算，也可以先简化为：

```text
slope = last - first
```

课程设计中推荐先用：

```text
slope = last - first
```

理由是实现简单、可解释性强。

---

### 7.2 缺失值处理

建议规则：

1. 若核心生命体征缺失严重，剔除该 stay。
2. 单个统计特征缺失时，用全队列中位数填充。
3. 实验室检查变量覆盖率较高，可以保留。
4. lactate 不纳入核心变量。

报告中可以写：

> 为保证轨迹向量维度一致，系统对缺失统计特征采用中位数填充，并删除覆盖率明显不足的乳酸变量。

---

### 7.3 特征标准化

由于不同指标量纲不同，必须标准化。

使用：

```python
sklearn.preprocessing.StandardScaler
```

标准化对象：

```text
72 维轨迹特征
```

治疗上下文标签不直接参与 StandardScaler，可以用于候选筛选或相似度加权。

---

### 7.4 治疗上下文匹配

推荐采用“先筛选，后计算距离”的方式。

流程：

```text
输入目标 stay_id
    ↓
读取目标患者治疗标签
    ↓
优先筛选治疗标签完全一致的候选患者
    ↓
如果候选数量不足，则允许部分标签一致
    ↓
在候选患者中计算轨迹距离
```

推荐规则：

```text
第一优先级：三个治疗标签完全一致
第二优先级：至少两个治疗标签一致
第三优先级：至少一个治疗标签一致
```

为了系统稳定，可以设置最小候选数：

```text
min_candidates = 100
```

若完全匹配候选少于 100，则放宽匹配条件。

这部分是高分点，因为它体现了对医疗数据中治疗混杂问题的考虑。

---

### 7.5 相似度计算

主方法使用欧氏距离。

对标准化后的轨迹特征向量：

```text
x_i = 患者 i 的 72 维轨迹向量
x_q = 目标患者 q 的 72 维轨迹向量
```

距离：

```text
distance(q, i) = sqrt(sum((x_q - x_i)^2))
```

距离越小，轨迹越相似。

为了前端显示更直观，可以把距离转换成相似度分数：

```text
similarity_score = 1 / (1 + distance)
```

Top-K 推荐：

```text
按照 distance 从小到大排序，返回 Top-K
```

推荐默认：

```text
K = 5 或 10
```

前端可以提供选项：

```text
Top-5
Top-10
Top-20
```

---

### 7.6 后续趋势评分

系统需要把相似患者后续 24h 的变化转化为可解释趋势。

建议定义一个简单的趋势评分：

对以下指标判断不利变化：

```text
heart_rate 上升明显
map 下降明显
spo2 下降明显
resp_rate 上升明显
creatinine 上升明显
bun 上升明显
wbc 上升明显
temperature 上升明显或异常
```

可以先采用规则阈值：

```text
heart_rate_delta > 10        → 不利变化 +1
map_delta < -5               → 不利变化 +1
spo2_delta < -2              → 不利变化 +1
resp_rate_delta > 3          → 不利变化 +1
creatinine_delta > 0.3       → 不利变化 +1
bun_delta > 5                → 不利变化 +1
wbc_delta > 2                → 不利变化 +1
```

然后：

```text
trend_score = 不利变化指标数量
```

趋势标签：

```text
trend_score >= 3  → 恶化
trend_score 1–2   → 稳定/轻度波动
trend_score 0     → 改善或稳定
```

更稳妥的标签可以设为：

```text
0–1: 稳定/改善
2–3: 波动
>=4: 恶化
```

但为了界面简单，建议最终使用三类：

```text
改善
稳定
恶化
```

注意：报告中要强调这是“数据分析规则”，不是临床诊断标准。

## 1. 课程设计定位

### 1.1 任务要求理解

本课程设计要求结合现实应用场景设计一个数据分析系统，报告中必须包含系统架构图及描述、应用层功能、数据存储层设计、数据分析层算法与工具、Python 等工具实现的应用界面，以及数据分析功能和最终分析结果。评分维度包括设计质量、能力水平和创新性。fileciteturn1file0

### 1.2 本项目的核心定位

本项目设计一个面向缺血性心脏病 ICU 患者的健康轨迹相似检索系统。用户选择一个目标患者 ICU stay 后，系统根据该患者 ICU 入科后前 24 小时的生命体征、实验室检查和治疗上下文，在历史患者轨迹库中检索最相似的患者，并展示这些相似患者在后续 24 小时内的健康变化趋势。

系统输出的不是“医学诊断”或“精准预测”，而是：

> 基于历史相似病例的后续趋势参考。

这个定位更适合课程设计，原因是它具有真实应用价值、系统结构完整、数据处理链路清楚，而且比传统“死亡风险预测”或“疾病分类”更有新颖性。

## 3. 选题价值与创新点

### 3.1 现实应用价值

ICU 患者在短时间内会产生大量生命体征、检验、治疗和结局数据。对于缺血性心脏病患者，医护人员不仅关心当前状态，还希望参考历史相似患者的后续变化，从而辅助判断患者是否可能趋于稳定、继续恶化或需要重点观察。

本系统以“相似病例检索”为核心，将历史患者数据转化为可查询、可对比、可解释的趋势参考工具。

### 3.2 与传统任务的区别

传统课程设计常见做法是：

```text
输入患者特征 → 训练分类模型 → 输出是否死亡/是否高危
```

本项目采用：

```text
输入目标患者当前轨迹 → 检索历史相似轨迹 → 展示相似患者后续变化 → 给出趋势参考
```

这个方案更像一个真实的数据分析系统，而不是单纯模型实验。

### 3.3 创新点

#### 创新点 1：健康轨迹相似检索

系统不直接做单点分类，而是将患者前 24 小时状态表示为健康轨迹特征向量，并从历史轨迹库中检索相似患者。

#### 创新点 2：相似病例后续趋势参考

系统不仅返回相似患者列表，还统计这些患者在 24–48 小时内的生命体征和实验室指标变化，用于辅助理解目标患者可能的后续发展方向。

#### 创新点 3：治疗上下文约束

系统加入循环支持、呼吸支持、液体管理三个治疗上下文标签，在相似检索时避免将治疗背景完全不同的患者直接比较，提高结果解释性。

#### 创新点 4：完整的数据系统链路

项目覆盖数据抽取、轨迹构建、特征存储、相似检索、趋势分析、可视化界面，符合大数据系统课程设计对系统性和工程能力的要求。

## 8. 数据分析方法设计

### 8.1 患者轨迹表示

每个患者的前 24 小时轨迹被表示为一个固定长度特征向量。

生命体征按 4 小时分箱，0–24h 共 6 个时间片：

```text
0–4h
4–8h
8–12h
12–16h
16–20h
20–24h
```

每个生命体征变量可以直接使用 6 个时间片的数值，也可以使用统计特征。

推荐主方案：

```text
使用 query_features_0_24h.parquet 中已经构建好的扁平特征。
```

如果需要在报告中解释，可以写为：

```text
系统将患者 0–24h 的生命体征时间序列、实验室检查汇总值和治疗上下文转换为固定长度特征向量，用于后续相似度计算。
```

### 8.2 特征标准化

由于不同变量量纲不同，例如心率、血压、肌酐、白细胞数值范围差异较大，因此相似度计算前必须进行标准化。

推荐方法：

```text
StandardScaler
```

公式：

```text
z = (x - μ) / σ
```

报告中说明：

> 标准化可以避免数值范围较大的指标在距离计算中占据过高权重。

### 8.3 治疗上下文匹配

治疗上下文包括：

```text
circulation_support
respiratory_support
fluid_management
```

推荐默认策略：

```text
优先检索治疗上下文完全一致的患者；
如果候选患者数量不足，则放宽为至少两个治疗上下文一致。
```

这样比硬筛选更稳，避免某些目标患者候选数量过少。

#### 推荐规则

```text
Step 1：筛选三个治疗上下文均一致的候选患者。
Step 2：如果候选数 ≥ 50，则在该集合中检索 Top-K。
Step 3：如果候选数 < 50，则放宽为至少两个上下文一致。
Step 4：如果仍不足，则使用全队列检索，但在结果中标记治疗上下文差异。
```

这个设计很实用，也能写成系统鲁棒性设计。

### 8.4 相似度计算

主算法使用标准化欧氏距离。

公式：

```text
distance(x, y) = sqrt(Σ(x_i - y_i)^2)
```

距离越小，患者轨迹越相似。

为了展示友好，可以将距离转换为相似度分数：

```text
similarity = 1 / (1 + distance)
```

或者归一化到 0–100：

```text
similarity_score = 100 × (1 - normalized_distance)
```

为了避免解释复杂，界面里可以显示：

```text
相似度分数：0.87
距离：1.42
```

主排序仍然使用距离。

### 8.5 后续趋势定义

后续趋势来自 `future_features_24_48h.parquet`。

建议趋势类别：

```text
改善
稳定
恶化
```

如果该文件中已经有趋势标签，直接使用。

如果需要本地 agent 重新定义，建议使用综合趋势评分：

不利变化包括：

```text
heart_rate 上升明显
map 下降明显
spo2 下降明显
resp_rate 上升明显
creatinine 上升明显
bun 上升明显
wbc 上升明显
hemoglobin 下降明显
```

有利变化包括：

```text
heart_rate 回落
map 稳定或改善
spo2 上升
resp_rate 回落
creatinine 下降或稳定
bun 下降或稳定
wbc 下降或稳定
```

可以构建：

```text
trend_score = 不利变化数量 - 有利变化数量
```

分类规则：

```text
trend_score >= 2：恶化
-1 <= trend_score < 2：稳定
trend_score <= -2：改善
```

课程设计报告中不要把这个说成医学金标准，而要说成：

> 基于多指标变化规则构建的趋势参考标签。

## 13. 风险与规避方案

### 13.1 风险：系统被认为不像“大数据”

规避：

强调 MIMIC-IV 多表数据、16,661 条 ICU stay、4 小时分箱轨迹、Parquet/DuckDB 存储和批量数据处理。

不要把项目写成“小模型训练”，而要写成“医疗轨迹数据分析系统”。

### 13.2 风险：相似检索被质疑不能预测未来

规避：

不要使用“精准预测”表述，统一使用：

```text
趋势参考
相似病例参考
辅助分析
历史轨迹对照
```

### 13.3 风险：治疗影响未来趋势

规避：

报告中明确加入治疗上下文匹配，并写：

> 为降低治疗混杂影响，系统在相似检索中引入循环支持、呼吸支持和液体管理三个治疗上下文。

### 13.4 风险：医学解释过度

规避：

所有建议都写成“重点关注指标”，不要写成治疗方案。

例如可以写：

```text
建议重点关注血氧、平均动脉压和肌酐变化。
```

不要写：

```text
建议使用某种药物或治疗方式。
```

### 13.5 风险：界面只有图，没有系统功能

规避：

Streamlit 必须包含交互：

```text
选择患者
选择 Top-K
是否启用治疗上下文
查看相似患者
查看趋势参考
```

这样才像应用层系统。
