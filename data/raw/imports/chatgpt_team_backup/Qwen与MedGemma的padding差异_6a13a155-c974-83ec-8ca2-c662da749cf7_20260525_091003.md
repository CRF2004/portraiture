## 🤖 Assistant (2026/5/25 09:10:03)

不是。**这段话的意思不是“Qwen 有 pad token、MedGemma 没有 pad token”。**

更准确地说，它在讲的是：

**Qwen 的 LoRA 训练过程中经常见过 padding 场景，而 MedGemma 的 LoRA 训练过程中基本没见过 padding 场景，所以推理时突然使用 left-padding，MedGemma 的 LoRA 行为可能不稳定。**

### 关键区别

#### 1. pad token 是“词表/模型配置”层面的东西

模型有没有 `pad_token_id`，取决于 tokenizer / config。

比如：

```python
tokenizer.pad_token
tokenizer.pad_token_id
model.config.pad_token_id
```

如果没有，也可以经常手动设置成：

```python
tokenizer.pad_token = tokenizer.eos_token
model.config.pad_token_id = tokenizer.eos_token_id
```

所以“有没有 pad token”是一个配置问题。

---

#### 2. “见过 padding”是训练数据分布问题

你引用的意思主要是这个。

Qwen 训练时：

```text
batch_size = 4
```

一个 batch 里有 4 条不同长度的样本。为了组成张量，框架会把它们 pad 到同样长度：

```text
样本 A: [token token token token]
样本 B: [pad   pad   token token]
样本 C: [pad   token token token]
样本 D: [token token token token]
```

如果是 left-padding，短样本左边会补 pad。

所以 Qwen 的 LoRA 在训练时就经常遇到：

```text
[PAD PAD PAD 正文正文正文]
```

这种输入结构。

---

MedGemma 训练时：

```text
batch_size = 1
```

每次只处理一条样本，不需要和别的样本对齐长度，所以通常不会产生 padding：

```text
[token token token token token]
```

因此它的 LoRA 训练过程中可能从没见过：

```text
[PAD PAD PAD 正文正文正文]
```

推理时你如果突然给它 left-padding：

```text
[PAD PAD PAD 问题内容]
```

模型主体可能还能靠 attention mask 处理，但 LoRA 适配器的行为不一定稳定，尤其是如果 position_ids、attention_mask、pad_token_id、generation 取最后 token 的逻辑有问题，就可能输出异常或直接崩。

---

### 但这段说法有点简化

严格来说，**只要 attention_mask、position_ids、pad_token_id 都处理正确，padding 理论上不应该严重影响有效 token 的输出。**

所以 MedGemma 出问题，不一定只是因为“LoRA 没见过 padding”。更常见的真实原因可能是：

1. `pad_token_id` 没设置，或者设置错了；
2. `pad_token` 被设成了不合适的 token；
3. left-padding 时 `position_ids` 没正确重算；
4. 推理代码用 `logits[:, -1, :]` 取最后位置，但最后位置可能不是有效 token；
5. attention mask 没正确传入；
6. 训练是 batch_size=1，无 padding，但推理 batch 推理时用了 padding，训练/推理分布不一致。

---

### 最直接的理解

这句话不是说：

```text
Qwen 有 pad token，MedGemma 没有 pad token
```

而是说：

```text
Qwen 的 LoRA 训练时见过 padding；
MedGemma 的 LoRA 训练时没见过 padding；
所以 MedGemma 推理时突然 left-padding，可能更容易出问题。
```

不过我会更谨慎地说：**真正要查的是 pad_token_id、attention_mask、position_ids 和推理取 logits 的逻辑，而不是简单归因于“MedGemma 没有 pad token”。**

## 🤖 Assistant (2026/5/25 09:14:33)

不一定能直接说“MedGemma 的适配器有问题、训练有问题”。

更准确是：

**MedGemma 的 LoRA 适配器本身未必坏了，但它的训练条件和推理条件不一致，导致推理时暴露出问题。**

你可以这样理解：

```text
训练时：
MedGemma LoRA 只见过无 padding 的单条样本

推理时：
突然给它 batch 推理 + left-padding

结果：
输入分布变了，LoRA 可能不稳，或者推理代码处理 padding 的逻辑有 bug
```

所以问题可能在三个层面：

### 1. 不是 LoRA “坏了”，而是没适应这种输入格式

如果训练时一直是：

```text
[正文 token token token]
```

推理时突然变成：

```text
[PAD PAD PAD 正文 token token token]
```

这属于**训练/推理分布不一致**。

这不等于适配器坏了，但说明它对 padding 场景没有鲁棒性。

---

### 2. 训练也不一定“错了”

`batch_size=1` 本身不是错。大模型显存不够时很常见。

但风险是：模型没有在训练中见过 padding。如果你推理时又必须 batch 推理，就最好训练时也模拟这种场景，比如：

```text
batch_size > 1
gradient_accumulation
packing=False
padding=True
```

或者至少让训练 collator 产生 padding。

所以更准确地说：

**训练没有错，但训练方式没有覆盖推理时会遇到的 padding 场景。**

---

### 3. 更常见的是推理 padding 逻辑有问题

尤其要查这些：

```python
tokenizer.pad_token
tokenizer.pad_token_id
model.config.pad_token_id
attention_mask
position_ids
tokenizer.padding_side
```

MedGemma 出问题时，我会优先怀疑：

```text
pad_token_id 没设好
attention_mask 没传对
left-padding 后 position_ids 没处理好
推理时取 logits 的位置错了
```

而不是马上断言：

```text
LoRA 适配器训练坏了
```

---

### 我的判断

可以说：

**MedGemma 这个 LoRA 适配器对 padding 不鲁棒，训练和推理不一致。**

但不建议说：

**MedGemma 适配器坏了。**

更不建议简单说：

**MedGemma 训练有问题。**

最准确的说法是：

> MedGemma 的 LoRA 是在 batch_size=1、无 padding 场景下训练出来的；如果推理时使用 left-padding batch 推理，就可能出现分布不一致。这个问题可能来自 LoRA 没见过 padding，也可能来自 pad_token、attention_mask、position_ids 或 generation 逻辑配置不正确。

## 3. decoder-only 模型批量生成时，通常还是应该 left-padding

不要因为 MedGemma left-padding 崩，就马上改成 right-padding。

Hugging Face 对 decoder-only LLM 的建议是：批量生成时输入长度不同，需要 padding，而这类模型不是训练来“从 pad token 后继续生成”的，所以要 left-padding，并且要传 `attention_mask`。citeturn598907search0

所以推理时一般应当是：

```python
tokenizer.padding_side = "left"
```

而不是：

```python
tokenizer.padding_side = "right"
```

如果 left-padding 崩，应该修配置或训练方式，而不是简单换 right-padding。

---

但注意，`gradient_accumulation_steps` 不能解决这个问题。它只是累积梯度，不会让单个 micro-batch 里出现多条不同长度样本。

这可以模拟 batch padding，不一定非要真实 batch_size>1。

### 方案 C：降低显存压力后再 batch_size=2


目标不是追求大 batch，而是让每个训练 step 里真实出现 padding。

## 方案 1：长度分桶 batch，最推荐先试

不要把长短差很多的样本放进同一个 batch。

比如不要这样：

```text
batch 1:
样本 A: 100 tokens
样本 B: 1800 tokens
样本 C: 230 tokens
样本 D: 1600 tokens
```

这样短样本会被 pad 很多。

改成这样：

```text
batch 1:
样本 A: 100 tokens
样本 B: 120 tokens
样本 C: 140 tokens
样本 D: 160 tokens

batch 2:
样本 E: 1500 tokens
样本 F: 1600 tokens
样本 G: 1700 tokens
样本 H: 1800 tokens
```

这样 padding 很少，速度比 `batch_size=1` 快很多，也比乱 batch 稳定。

简单写法：

```python
def bucket_by_length(texts, tokenizer, batch_size=4):
    items = []
    for text in texts:
        ids = tokenizer(text, add_special_tokens=True)["input_ids"]
        items.append((len(ids), text))

    items.sort(key=lambda x: x[0])

    batches = []
    for i in range(0, len(items), batch_size):
        batch = [x[1] for x in items[i:i + batch_size]]
        batches.append(batch)

    return batches
```

推理：

```python
tokenizer.padding_side = "left"
tokenizer.pad_token = tokenizer.eos_token
model.config.pad_token_id = tokenizer.eos_token_id
model.generation_config.pad_token_id = tokenizer.eos_token_id

for batch_texts in bucket_by_length(texts, tokenizer, batch_size=4):
    inputs = tokenizer(
        batch_texts,
        return_tensors="pt",
        padding=True,
        truncation=True,
    ).to(model.device)

    outputs = model.generate(
        **inputs,
        max_new_tokens=512,
        pad_token_id=tokenizer.pad_token_id,
        eos_token_id=tokenizer.eos_token_id,
    )
```

这个方案适合你现在的情况：**不用重训，先把速度拉回来一部分。**

## 方案 3：用更强的推理引擎，比如 vLLM

可以试 vLLM。vLLM 官方文档强调它支持 PagedAttention、continuous batching、chunked prefill 和 prefix caching，这些就是为高吞吐推理服务设计的。citeturn864127search1

如果你用的是 **MedGemma 27B multimodal**，要小心图像输入、processor、LoRA target modules 的兼容性。

## 方案 4：短补训 LoRA，让它见过 left-padding

如果你最终必须稳定 batch 推理，那最好做一次“padding 适应性补训”。


目标不是让模型学新知识，而是让 LoRA 适应这种输入形态：

```text

```

这个叫“补训鲁棒性”，不是从头重训。

解释一下：

`--padding_side left` 很关键。ms-swift 文档明确说，训练时 `batch_size >= 2` 时这个参数才生效；并且推理时如果 `batch_size >= 2`，只会使用 left-padding。citeturn532574view0

`--per_device_train_batch_size 2` 也很关键。**注意不是 total batch size >= 2，而是每张卡上的 micro-batch 要 >= 2。**因为 padding 是在每个 dataloader batch 内发生的。`gradient_accumulation_steps` 只能累积梯度，不能让单个 micro-batch 里出现 padding。ms-swift 文档里也说明 total batch 是由 `per_device_train_batch_size * gradient_accumulation_steps * world_size` 算出来的，但这不等于 micro-batch 里有多条样本。citeturn553341view2

`--packing false` / `--padding_free false` 是为了**不要绕开 padding**。ms-swift 的 `padding_free` 和 `packing` 都是为了减少或避免 padding、提高训练效率；但你这次的目标正好相反：让 LoRA 见过 padding。citeturn553341view1

## 推荐命令：MedGemma 27B text-only

如果你用的是 `google/medgemma-27b-text-it`，可以按这个方向：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 \
swift sft \
  --model google/medgemma-27b-text-it \
  --train_type lora \
  --dataset /path/to/train.jsonl \
  --val_dataset /path/to/val.jsonl \
  --torch_dtype bfloat16 \
  --quant_method bnb \
  --quant_bits 4 \
  --bnb_4bit_quant_type nf4 \
  --bnb_4bit_compute_dtype bfloat16 \
  --per_device_train_batch_size 2 \
  --per_device_eval_batch_size 2 \
  --gradient_accumulation_steps 8 \
  --padding_side left \
  --packing false \
  --padding_free false \
  --group_by_length false \
  --max_length 2048 \
  --truncation_strategy delete \
  --learning_rate 1e-4 \
  --lora_rank 16 \
  --lora_alpha 32 \
  --lora_dropout 0.05 \
  --target_modules q_proj k_proj v_proj o_proj gate_proj up_proj down_proj \
  --gradient_checkpointing true \
  --save_steps 200 \
  --eval_steps 200 \
  --save_total_limit 3 \
  --num_train_epochs 2 \
  --output_dir output/medgemma27b_lora_leftpad
```

ms-swift 的 LoRA 参数包括 `lora_rank`、`lora_alpha`、`lora_dropout`，默认分别是 8、32、0.05；`target_modules` 默认是 `all-linear`，也可以显式指定 `q_proj/k_proj/v_proj/o_proj/gate_proj/up_proj/down_proj` 这些模块。citeturn229242view0turn229242view1

## 如果 27B 还是塞不下 batch_size=2

那就按这个顺序降显存：

### 1. 先降 `max_length`

比如从：

```bash
--max_length 2048
```

降到：

```bash
--max_length 1536
```

甚至：

```bash
--max_length 1024
```

你当前问题是 padding 适配，不是追求最长上下文。先让 micro-batch 能到 2，比长上下文更重要。

### 2. 保持 QLoRA

也就是：

```bash
--quant_method bnb
--quant_bits 4
```

ms-swift 当前参数里，加载量化模型用 `quant_method` 和 `quant_bits`，4-bit BNB 还可以设置 `bnb_4bit_compute_dtype` 和 `bnb_4bit_quant_type`。citeturn553341view0

### 3. 用多卡 ZeRO

比如：

```bash
--deepspeed zero2
```

或者显存更紧张时：

```bash
--deepspeed zero3
```

ms-swift 支持内置 DeepSpeed 配置，包括 `zero0/zero1/zero2/zero3/zero2_offload/zero3_offload`。citeturn553341view2

### 4. 还不行，就只能自定义 collator

如果你无论如何只能：

```bash
--per_device_train_batch_size 1
```

那标准 collator 下还是不会产生 padding。此时要做一个自定义数据处理/插件：**即使单条样本，也随机 left-pad 到更长长度**。

目标是构造这种训练输入：

```text
[PAD PAD PAD PAD 正文 token token token]
```

同时保证：

```text
attention_mask: PAD 位置为 0
labels: PAD 位置为 -100
```

这个方案比 batch_size=2 麻烦，但本质上可以解决“LoRA 没见过 left-padding”的问题。

## 多模态 MedGemma 的注意点

如果你用的是：

```bash
google/medgemma-27b-it
```

而不是：

```bash
google/medgemma-27b-text-it
```

那它是 `gemma3_vision` 类型。ms-swift 文档里对多模态 LoRA 有个重要行为：`target_modules='all-linear'` 时，默认 LoRA 主要加在 LLM 部分；`freeze_vit` 和 `freeze_aligner` 默认会影响视觉塔和对齐层是否加 LoRA。citeturn229242view1

如果你的任务是纯文本 checker，我建议直接用：

```bash
google/medgemma-27b-text-it
```

不要用多模态版。少一层 processor / image token / vision tower 复杂度，padding 问题更容易收敛。

## 训练后必须做的验证

重新训完不要直接上全量推理，先测这三个：

```python
# 1. 单条
[prompt_a]

# 2. 两条等长
[prompt_a, prompt_a]

# 3. 两条不同长度，left-padding
[short_prompt, long_prompt]
```

第三个正常，才说明这次 LoRA 真的适配了 batch left-padding。

## 结论

可以让 swift 的 LoRA 适配 MedGemma。你这次最关键的不是换模型，而是训练命令里必须做到：

```bash
--per_device_train_batch_size 2
--padding_side left
--packing false
--padding_free false
```

并且推理也保持：

```python
tokenizer.padding_side = "left"
```

这才是训练/推理一致。否则你重新训一遍，但还是 `batch_size=1` 无 padding，问题大概率还会复现。
