## 🤖 Assistant (2026/5/25 19:17:15)

是的，但要分清楚：**MCP 不能把一个纯文本基座模型“变成真正多模态模型”**。它最多是给 Claude Code 接一个“看图工具”。这个工具可以有两种实现。

## 1. 真多模态路径：MCP 把图片作为 image content 交给模型

MCP 协议本身支持工具返回 `image` 类型内容，比如 base64 图片数据和 `mimeType: image/png`。这说明从协议层面，MCP 不只支持纯文本，也可以传图片。citeturn133875view0

但前提是：

**Claude Code 客户端要把这个 image content 正确传给模型，而且模型本身要有视觉能力。**

如果你用的是 Anthropic Claude 官方视觉模型，理论上这是可行方向。Claude API 本身支持 images and vision，Anthropic 也在 2026 年的发布说明里提到新版 Opus 视觉能力提升。citeturn281197view2turn281197view3

但如果你的 Claude Code 后端接的是 **DeepSeek / 文本模型 / 非视觉兼容 Anthropic proxy**，那即使 MCP 返回图片，模型也未必能看懂。它可能只看到“这里有个图片块”，甚至完全不支持。

## 2. 更常见路径：Vision MCP 调用外部视觉模型，把图片转成文本

你说的这种判断基本对：很多所谓“让 Claude Code 看图”的 MCP，本质是：

> Claude Code 调用 MCP → MCP 读取图片 / 截图 → MCP 调用 Gemini / GPT-4o / Qwen-VL / GLM-V / OCR → 返回一段文字描述给 Claude Code

这对文本基座模型也有效，因为最后回到 Claude Code 的是纯文本。例如：

```text
图片中是一个登录页，左侧为 logo，右侧有用户名、密码输入框，按钮颜色为蓝色……
```

这种方案不是“模型亲眼看图”，而是“外部视觉模型代看，然后把结果转述给它”。

## 3. 对你这种 Claude Code + DeepSeek backend，更现实的是第二种

结合你前面那个 DeepSeek backend 脚本，你现在更适合用：

```text
Claude Code / DeepSeek
        ↓ 调 MCP
Vision MCP / Screenshot MCP / OCR MCP
        ↓ 调视觉模型
Gemini / Qwen2.5-VL / GLM-4V / GPT-4o-mini-vision
        ↓ 返回文本描述
Claude Code 根据描述继续写代码、改 UI、分析图像
```

这不是坏方案，实际工程里很常用。特别是做 UI 调试、截图分析、论文框架图检查、OCR、报错截图识别，已经够用了。

## 4. 但它有明显局限

最大问题是：**信息会被压缩成文本，细节会丢。**

比如你让它检查 UI，它可能能说：

```text
按钮偏右，标题过大，卡片间距不一致。
```

但它未必能精确判断：

```text
第 3 个卡片左边距比第 2 个多 6px；
图标 baseline 和标题文字没有对齐；
蓝色主色与整体风格不一致。
```

除非你的 Vision MCP 专门设计成结构化输出，例如返回：

```json
{
  "layout_issues": [...],
  "text_recognition": [...],
  "bbox": [...],
  "suggested_css_changes": [...]
}
```

所以如果你要做 UI 迭代，别只让它“描述图片”。最好让 MCP 返回 **结构化视觉分析**，比如 OCR 文本、元素位置、颜色、布局问题、疑似 CSS 修改建议。

## 5. 推荐你采用的方案

如果你的目标是让 Claude Code 能处理截图、网页 UI、论文图、PPT 页面，我建议按这个优先级：

**最实用：Vision MCP + 截图路径**

```text
take_screenshot(path/url)
analyze_image(image_path, task)
compare_images(before, after)
ocr_image(image_path)
```

其中 `analyze_image` 不要只返回自然语言，最好返回：

```json
{
  "summary": "...",
  "detected_text": [...],
  "layout": "...",
  "issues": [...],
  "actionable_changes": [...]
}
```

**如果是前端 UI：再加 Playwright MCP / Chrome DevTools MCP**

Playwright 可以让 agent 打开页面、截图、拿 DOM、看 console、点按钮。视觉模型负责“看起来对不对”，Playwright 负责“页面结构和交互有没有问题”。这比单纯看截图强很多。

## 结论

你的理解基本正确：

**MCP 可以让 Claude Code“具备看图能力”，但多数情况下不是让基座模型本身多模态，而是外挂一个视觉模型/OCR工具，把图片变成文本或结构化结果。**

对你现在这种 DeepSeek backend 来说，这反而是最稳的方案。不要纠结“真假多模态”，关键是把 MCP 工具设计好：截图、OCR、视觉分析、前后对比、结构化输出。这样 Claude Code 就能闭环做 UI、图表、论文图、PPT 页面检查。

## 1. Figma：可以，但主要是“矢量化”，不等于语义识别

Figma 现在有 **Vectorize**，可以把 raster 图片转成可编辑向量，让你在 Figma 里缩放、修改路径。Figma 官方说它可以把 raster images 转成 editable vectors。citeturn252233search12

```text

```

不是：

```text
框架图 → 卡片、标题、箭头、文本框、图标、分组
```

所以如果你传入一张论文框架图 PNG，Figma 可能能把线条和形状变成路径，但**文字未必变成真正可编辑文本，箭头未必识别成连接线，卡片也未必是独立组件**。后续要改结构时会比较痛苦。

```text
一张静态图片 → 多个可编辑图层
```
