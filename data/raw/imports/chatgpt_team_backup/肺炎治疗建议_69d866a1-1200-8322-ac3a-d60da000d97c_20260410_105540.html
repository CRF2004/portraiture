你的目标本质上是：把“解释型评审（judge_reason）”→“可操作的错误标注（checker output）”，用于驱动后续的 rewriter agent。关键是去解释化、去冗余、结构化定位问题。

下面给你一个可直接落地的转换范式。

---

# 一、目标结构（Checker Agent Output Schema）

建议统一成这种最小充分结构：

{
  "issues": [
    {
      "id": "ISSUE_1",
      "type": "missing | incorrect | overincluded | instruction_violation",
      "criterion": "...",
      "span": "text span or section",
      "description": "问题本身（去解释化）",
      "evidence": "来自原judge_reason的最小引用"
    }
  ]
}


### 字段说明（非常关键）
- type（问题类型）
- missing：缺失要求内容
- incorrect：事实或逻辑错误
- overincluded：不该出现却出现（⚠️你这个case里“列出抗生素”属于这个）
- instruction_violation：没遵循明确指令（如必须声明不能开药）

- span（问题位置）
- 如果你有原回答 → 用原文片段
- 如果没有 → 用 "global" 或 "introduction" / "antibiotics section"

- description
- 必须是可执行的错误陈述
- ❌ 不要写：“没有很好地强调……”
- ✅ 要写：“未在开头声明不能开具药物”

---

# 二、转换规则（从 judge_reason → checker）

逐条规则讲清楚：

---

## 1️⃣ satisfied = false → 一定生成 issue（核心）

## 2️⃣ satisfied = true + points < 0 → “不该做却做了”（高优先级）

- 不要被 satisfied=true 迷惑

## 3️⃣ satisfied = true + points > 0 → 忽略（不用输出）

这些是“做对的地方”，checker 不关心。
