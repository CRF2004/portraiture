🤖Assistant2026/5/26 19:08:14
从视频看，这不是普通网页动效，而是网页里嵌了一个 3D 互动场景，本质上有点像“轻量网页游戏”。

它大概率是这么做的：

核心技术：WebGL / Three.js / Babylon.js / Unity WebGL

用户在网页里控制一个角色走动，镜头跟随角色，场景是 3D 城市/店铺/展厅。这类效果一般由下面几层组成：

1. 3D 场景
用 Blender、Spline、Sketchfab、Unity Asset Store 之类的工具做街道、建筑、人物模型，然后导出成 .glb / .gltf。

2. 网页渲染引擎
用 Three.js、React Three Fiber、Babylon.js，或者 Unity WebGL，把 3D 模型显示在浏览器里。

3. 角色控制
给角色加键盘控制，比如 WASD / 方向键移动，手机端可以做虚拟摇杆。

4. 镜头跟随
摄像机跟着人物移动，类似第三人称游戏视角。

5. 碰撞检测
防止角色穿墙、掉出地图。常见方案是 Cannon.js、Rapier、Ammo.js，或者自己写简单碰撞。

6. 网页 UI 叠加
上面的按钮、文字、品牌介绍、弹窗，其实可以是普通 HTML/CSS 盖在 3D canvas 上。

如果它是 WordPress 网站，那 WordPress 只是外壳，真正酷的部分通常是：

> Three.js / Unity WebGL 做好互动场景，然后通过 iframe、短代码 shortcode、自定义插件或页面组件嵌进 WordPress。

比较现实的实现路线有三种：

最快路线：Spline / Dora / Framer + 3D 嵌入
适合做酷炫展示页，不需要太复杂的游戏逻辑。

专业前端路线：Three.js + React Three Fiber
适合做定制互动网站、品牌官网、虚拟展厅、产品体验页。

游戏路线：Unity 导出 WebGL
适合角色移动、任务、NPC、复杂交互，但文件更大，加载和手机性能要处理好。

如果你想做视频里这种，我会建议技术栈这样选：

React / Next.js
+ React Three Fiber
+ Drei
+ Rapier 物理引擎
+ Blender / GLB 模型
+ GSAP 做页面转场动画
+ WordPress 用 iframe 或插件嵌入


简单说，它不是“某个普通插件一键生成”的效果，而是把网页、3D 建模、游戏控制、前端动画结合起来做的。视频标题里提到 WordPress 互动插件，可能是他们把这个 3D 互动模块包装成了 WordPress 插件/组件，但底层仍然是 WebGL。

🤖Assistant2026/5/26 19:10:31
对，网页真的能做到，而且不一定需要 WebGPU。

你视频里这种效果，WebGL + Three.js 就足够做出来。WebGPU更像是下一代图形接口，性能潜力更强，但目前还不是所有浏览器都完整支持，MDN 仍把 WebGPU 标为“Limited availability”，并且需要 HTTPS 安全环境。citeturn984118search0 Three.js 现在也有 WebGPU 渲染器，但它默认会在支持时用 WebGPU，不支持时回退到 WebGL 2。citeturn984118search4

真正影响加载速度的，不是“用了 WebGPU 还是 WebGL”，而是这些东西：

1. 3D 模型有多大
如果整个城市、人物、材质都没优化，一个 .glb 可能几十 MB 到上百 MB，第一次打开肯定慢。

2. 贴图有没有压缩
很多网页 3D 卡顿不是模型问题，是图片贴图太大。比如一个建筑贴图用 4K PNG，几个贴图就爆了。

3. 有没有分批加载
好的做法不是一次把整座城市加载完，而是先加载主角附近区域，远处低清或延迟加载。

4. 有没有用模型压缩
常见会用 Draco、Meshopt、KTX2、Basis 等压缩方案。像 glTF Transform 这类工具就是专门用来处理、优化、压缩 glTF/GLB 模型的。citeturn984118search11

5. 场景是不是“假复杂”
很多酷炫网站其实很聪明：
远处建筑是低模，不能进入的地方只是贴图；天空、灯光、反射很多是烘焙好的；角色活动范围也很小。看起来像开放世界，其实是精心布置的小场景。

所以加载体验通常会是这样：

优化得好：
首屏 2-5 秒左右出现
后台继续加载细节

一般水平：
5-15 秒，有 loading 页面

没优化：
20 秒以上，手机可能直接卡死


WebGPU能提升一些渲染和计算能力，Chrome 开发者文档也提到 WebGPU 可以降低 JavaScript 工作负载、提供 WebGL 没有的一些高级 GPU 能力。citeturn984118search12 但对这种“网页小型 3D 互动场景”来说，WebGL 仍然是更稳的主力方案。

你觉得它很难实现是对的，但可以拆开看：

初级难度：
做一个 3D 模型展示页

中级难度：
加镜头移动、点击交互、滚动动画

高级难度：
加人物控制、碰撞、地图、任务、移动端适配

很高级：
多人在线、实时聊天、换装、复杂物理、动态光照


你视频里的这种大概属于：

> 高级前端 + 轻量游戏开发 + 3D 美术优化

不是普通网站开发，但也不是非得大团队。一个熟 Three.js/React Three Fiber 的开发者，加一个会 Blender 优化模型的人，就能做出类似的原型。

最现实的技术路线是：

Next.js / React
+ Three.js 或 React Three Fiber
+ Drei 辅助工具
+ Rapier 做碰撞/物理
+ Blender 做模型优化
+ GLB/GLTF 格式
+ GSAP 做网页动画


一句话：难点不是浏览器能不能做，而是你会不会把“游戏级画面”压缩成网页能流畅加载的东西。这就是这类网站真正厉害的地方。

## 最适合你的美术素材库

1. Kenney
非常适合低多边形、卡通、游戏风格网页。它有 2D、3D、UI、音效等大量免费游戏素材，很适合做虚拟城市、商店、展厅原型。citeturn631426search1turn631426search4

2. Quaternius
也很适合你视频那种低模 3D 世界。它主打免费的 Low Poly 3D 模型，而且官方写的是 CC0 License。citeturn631426search2turn631426search32

3. Poly Haven
如果你想画面更真实，找 HDRI、PBR 材质、真实扫描模型，用这个。它的资产是 CC0，官方说明可用于任何目的，无需注册下载。citeturn688810search0turn688810search8

4. ambientCG
适合找地面、墙面、砖块、金属、木材这类 PBR 材质。官方介绍它是大型免费 PBR materials、HDRIs 和 models 来源。citeturn688810search1

5. Sketchfab 免费模型区
东西很多，但要小心许可证。Sketchfab 免费模型可能是 Creative Commons，不一定都是 CC0，有些需要署名，有些不能商用或不能改。citeturn688810search2turn688810search6

6. Mixamo
适合做人形角色动画，比如走路、跑步、跳跃、挥手。它不是开源素材库，但 Adobe 社区 FAQ 里说明 Mixamo 在技术预览期间可免费用于商业和非商业项目，无授权费/版税；不过我会把它当“免费工具”，不要当 CC0 开源资产。citeturn688810search3turn688810search11

## 比较值得看的开源仓库/模板

1. React Three Fiber
这是 React 里做 Three.js 的主流方案。官方描述它是 Three.js 的 React renderer，可以用组件化方式写 3D 场景。citeturn493786search2

2. pmndrs/react-three-next
Next.js + React Three Fiber 的极简 starter。适合做“网页 + 3D canvas 混合”的项目。citeturn631426search18

3. pmndrs/drei
这是 React Three Fiber 的常用辅助库，里面有很多现成组件，比如相机控制、加载器、环境光、文字、HTML 叠加等。citeturn631426search17

4. pmndrs/ecctrl
这个很接近你视频里的核心：网页里的角色控制器。它基于 React Three Fiber 和 react-three-rapier，提供了可试玩的 character controller playground。citeturn493786search5

5. doppl3r/kinematic-character-controller-example
一个 Rapier.js + Three.js 的角色控制示例，重点是 Kinematic Character Controller，也就是“角色怎么走、怎么碰撞、怎么不穿墙”。citeturn493786search34

6. icurtis1/character-controller-sample-project
这个是 React Three Fiber + Rapier 的第三人称角色控制示例，还包含移动端支持、物理交互和后处理效果，适合学习“像游戏一样控制人物”的部分。citeturn493786search24

7. Webaverse
如果你想看更完整的“网页元宇宙/虚拟世界引擎”，可以看 Webaverse。它是开源 web metaverse game engine，基于 three.js、Node 等技术，但对新手来说偏重。citeturn493786search7turn493786search22

## 我建议你的起步组合

最现实的一套是：

Next.js
+ React Three Fiber
+ Drei
+ Rapier / react-three-rapier
+ ecctrl 角色控制器
+ Kenney / Quaternius 低模素材
+ Poly Haven / ambientCG 材质和环境光


这样你不用一开始就自己写完整游戏引擎。

## 想复刻你视频那种，路线可以这样走

第一步，先做一个小地图：地面、几栋建筑、几个道具。素材用 Kenney 或 Quaternius。

第二步，加一个可控制角色：先用 ecctrl 或 character controller 示例，不要自己从零写碰撞。

第三步，加镜头跟随、移动端控制、loading 页面。

第四步，再慢慢加交互：走到门口弹窗、点击 NPC、进入商店、显示产品卡片。

这类项目最容易踩坑的地方不是“找不到素材”，而是素材风格不统一。所以前期最好只选一个风格：比如全部 low-poly，别把写实模型、卡通模型、扫描模型混在一起。

## 1. 有角色控制器，但不是完整艺术网站

比如 pmndrs/ecctrl 是 React Three Fiber 生态里的角色控制器，支持角色移动、小障碍、物理交互、固定相机模式等，很适合做“人物真的在场景里走”的部分。citeturn434187view0

还有 pmndrs/BVHEcctrl，它不依赖完整物理引擎，用 three-mesh-bvh 做碰撞检测，更适合轻量网页 3D 体验、互动作品集、虚拟世界。citeturn434187view1

所以人物移动这块有现成基础。

## 2. 有 tiny planet / low-poly 星球项目，但偏生成实验

GitHub 的 low-poly 主题里确实能找到 flo-bit/tiny-planets 这种“浏览器里程序化生成小星球”的项目，描述就是 procedurally generated tiny planets in the browsers。citeturn434187view2

但这类通常是“看一个小球”，不是你要的“站在大星球表面，看不到完整球体，只感到地平线弯曲”。

你要的其实更接近：

大半径球面 / 弯曲地形
+ 人物真实移动
+ 低机位广角镜头
+ fisheye / barrel distortion
+ 强漫画后处理


不是普通 tiny planet demo。

## 最重要的 8 个问题

### 1. ui-safe 相机模式有 bug

你的类型里是：

| 'ui-safe'


但 cameraPresets 里写的是：

uiSafe: {
  id: 'ui-safe',
}


然后代码用：

cameraPresets[currentMode]


所以当 currentMode === 'ui-safe' 时，其实拿不到 uiSafe，会 fallback 到 explore。

应该改成：

export const cameraPresets: Record<CameraMode, CameraPreset> = {
  explore: {...},
  interaction: {...},
  cinematic: {...},
  inspection: {...},
  'ui-safe': {
    id: 'ui-safe',
    fov: 56,
    distance: 6.2,
    height: 2.6,
    lookAtHeight: 1.2,
    followSharpness: 0.08,
    rotationSharpness: 0.08,
    barrelDistortion: 0
  }
}


这个是必须优先修的。

---

### 2. 弯曲世界现在是“视觉弯曲，物理不弯曲”

CurvedWorld.tsx 里视觉平面用了 shader：

worldPosition.y -= pow(dist, 2.0) * uCurvature;


但物理碰撞是一个平的 CuboidCollider。

这会导致一个问题：走远之后，视觉地面已经往下弯了，但人物物理上还站在 y=0 的平地上。短距离看不明显，范围大了就会出现人物漂浮、物件不贴地、交互距离不准。

你有两个路线：

路线 A：假弯曲，适合产品界面
保持物理世界是平的，只把远景、建筑、地平线做弯曲。近处角色和交互点不要强弯曲。这个最稳。

路线 B：真球面/真曲面，适合游戏化世界
角色真的沿球面法线移动，重力方向也跟着变化。这更酷，但复杂很多，第一版不建议。

我建议第一版走路线 A：大半径视觉弯曲 + 平面物理交互。但是要明确限制：玩家主要活动区域不要离原点太远，远处只做视觉张力。

---

### 3. CameraRig 还没有真正“有张力”

现在 CameraRig 是跟随玩家位置，但相机偏移基本固定在世界坐标：

const idealOffset = new THREE.Vector3(0, preset.height, -preset.distance);
const targetPos = new THREE.Vector3().copy(playerPos).add(idealOffset);


这会导致相机不是严格跟随角色朝向，而是一直从世界 Z 方向看。对 demo 可以，但要做你想要的视频感，应该让镜头跟角色方向、移动方向、交互对象动态变化。

建议下一版 CameraRig 支持：

explore-wide      // 低机位、广角、探索
dialog-close      // NPC 对话时拉近
object-inspect    // 看电话亭/汽车/产品塔
product-reveal    // 产品展示大镜头
ui-safe           // 阅读面板时稳定构图
debug-free        // 开发调试自由镜头


目前 barrelDistortion、shoulderOffset 已经写在 preset 里，但没有真正使用。这个很好，说明方向对；下一步要把它落地。

---

### 4. InteractionPoint 的接口方向很好，但执行逻辑还太硬

你现在的 InteractionPointDefinition 设计得不错：

visual
triggers
actions
conditions
metadata


这已经是可扩展系统的雏形。

但实现里有几个问题：

- 只执行第一个 action。
- triggers 定义了很多类型，但实际只做了 proximity 和 click。
- conditions、cooldownMs、once 还没实现。
- click 触发逻辑写在 InteractionPoint，E 键触发逻辑写在 InteractionSystem，重复了。
- panel 打开逻辑直接写死，没有统一 dispatcher。

应该增加一个核心模块：

InteractionDispatcher


它负责：

executeInteraction(id, triggerType)
executeAction(action)
checkConditions()
handleCooldown()
handleOnce()
emitWorldEvent()


这样以后接不同应用时，不用每个物体自己处理逻辑。

## 现在还剩几个发布前必修点

### 1. 还有 AI Studio 残留

项目里还有：

metadata.json
.env.example


而且 .env.example 还在写：

GEMINI_API_KEY
APP_URL
AI Studio automatically injects...


但现在项目已经是前端 kit，不需要 Gemini。

建议：

删除 metadata.json
重写 .env.example


或者第一版干脆不要 .env.example。

否则别人打开 GitHub 会误以为这个项目依赖 Google AI Studio / Gemini 后端。

---

### 2. README 里的目录结构和真实目录不一致

README 写的是：

src/core
src/components/visuals
src/ui/panels


但真实结构是：

src/interaction
src/camera
src/player
src/world
src/ui
src/adapters


这个要改。README 是开源项目的门面，不能写和项目不一致的架构。

---

### 3. CameraMode 类型比实际 preset 多

类型里有：

'explore' | 'interaction' | 'cinematic' | 'inspection' | 'ui-safe'


但 cameraPresets 现在只有：

explore
interaction
ui-safe


如果某处切到 inspection 或 cinematic，会 fallback 到 explore。

建议补齐：

export const cameraPresets: Record<CameraMode, CameraPreset> = {
  explore: {...},
  interaction: {...},
  inspection: {...},
  cinematic: {...},
  'ui-safe': {...}
}


不要用：

Record<string, CameraPreset>


要改成：

Record<CameraMode, CameraPreset>


这样 TypeScript 会强制你补全。

---

### 4. barrelDistortion 还只是配置，没有真正生效

你现在 camera preset 里有：

barrelDistortion: 0.12


但实际后处理里还没有使用它。

也就是说现在“广角张力”主要来自 FOV，不是真正的镜头畸变。
这不影响 alpha，但 README 里不要说得太满。可以写：

Camera presets include fields for barrel distortion; full distortion pass is planned.


后续可以加一个 custom postprocessing effect，或者先用更夸张的 FOV + 构图解决。

---

### 5. InteractionDispatcher 有了，但还没完全干净

现在它已经统一执行 action，这是好事。
但里面还有几个临时实现：

interactionId: 'unknown'
triggerType: 'proximity'
player: {} as any
world: {} as any
runCommand: async (id, p) => ({ ok: true })
checkConditions() 永远 return true


这说明 dispatcher 现在是“骨架可用”，但还不是稳定 API。

建议下一步改成：

executeInteraction(id, triggerType, context?)


然后 action 执行时把真实 context 传进去：

{
  interactionId: id,
  triggerType,
  player,
  app: activeAdapter,
  world: activeWorld,
  openPanel,
  closePanel,
  setCameraMode,
  runCommand,
  emit,
  getState
}


另外现在 trigger 的 metadata 是直接改对象：

trigger.metadata.lastExecutedAt = Date.now()


这在 Zustand 里不太好，因为你是在 mutating store 里的 definition。以后应该把 cooldown / once 状态单独放到 runtime state：

interactionRuntimeState: Record<string, {
  executedTriggers: string[]
  lastExecutedAt: number
}>


---

### 6. vehicle 类型还没实现

你的类型里允许：

'vehicle'


但 visualRegistry 里没有 vehicle：

npc
phone-booth
building
portal
crate


所以未来写：

visual: { type: 'vehicle' }


会 fallback 到 crate。

你之前很在意汽车、电话亭、NPC 这些产品隐喻，所以建议加一个默认 VehicleVisual。

---

### 7. visual type 现在不够开放

现在类型是：

type: 'npc' | 'phone-booth' | 'vehicle' | 'building' | 'portal' | 'crate' | 'custom'


但你又做了：

registerVisual(type, component)


这两个设计有点冲突。

如果别人注册：

registerVisual('github-repo', GithubRepoVisual)


TypeScript 那边 visual.type 不让他写 'github-repo'。

建议改成：

export type BuiltInVisualType =
  | 'npc'
  | 'phone-booth'
  | 'vehicle'
  | 'building'
  | 'portal'
  | 'crate'

export interface InteractionVisualDefinition {
  type: BuiltInVisualType | (string & {})
  ...
}


这样既保留内置提示，也允许外部扩展。

---

### 8. 默认 visual 还没有“站在地上”

比如：

<boxGeometry args={[1, 2, 1]} />


Three.js 的 box 默认中心在原点，所以电话亭会有一半在地面下。building 也是：

<boxGeometry args={[3, 5, 3]} />


会有 2.5 米在地下。

要么每个 visual 内部上移：

<mesh position={[0, height / 2, 0]}>


要么让 registry 组件遵循一个规则：

所有 visual 的 local origin 必须在地面接触点


这个规则要写进 README / docs。

---
