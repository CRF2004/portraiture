1. 有角色坐标和路径规划；
2. 有点击角色/点击座位的交互；
3. 有布局系统；
4. 有 sub-agent 和 parent-agent 的关联概念；

## 一、群组机制：不要只是“站在一起”，而是变成任务小队

你说的“让角色走到一起形成群组”，我觉得可以设计成几种很自然的交互。

### 1. 拖拽组队：把 Agent 拖到一起形成小队

交互可以这样：

用户拖动 Agent A 到 Agent B 附近，出现提示：

> 创建协作小队？

然后生成一个小队区域，比如一个发光圆圈 / 小会议桌 / 临时白板。

小队形成后，UI 上显示：

```text
Bug 修复小队
成员：Planner、Coder、Reviewer
目标：修复登录接口 500 错误
状态：Coder 正在修改，Reviewer 等待 diff
```

这就不是单纯“角色靠近”，而是一个真实的 task container。

---

### 2. 框选组队：像 RTS 游戏一样框选多个 Agent

适合多个 Agent 场景。

用户用鼠标框选 3 个角色，然后右键 / 点击菜单：

```text
创建小队
分配任务
移动到会议区
解散小队
```

这会比拖来拖去更高效，尤其你后面 Agent 多了以后。

---

### 3. 会议区：让群组有“空间语义”

你可以在办公室里放几个特殊家具：

| 家具 / 区域 | 功能 |
|---|---|
| 会议桌 | 多 Agent 讨论、规划任务 |
| 白板 | 展示当前计划、todo、架构图 |
| 工位 | 单 Agent 执行代码任务 |
| Review 区 | 展示 diff、测试结果、review comment |
| Debug 角落 | 显示 logs、error stack |
| 休息区 | 空闲 Agent 待机行为 |

这样用户看到角色在哪里，就知道它在干什么。

比如：

- Agent 坐在工位：正在执行；
- Agent 站在白板前：正在规划；
- 两个 Agent 在会议桌：正在同步；
- Reviewer 站在 Coder 后面：正在 review；
- Agent 在沙发：空闲或等待输入。

这就会非常有画面感。

---

## 二、群组的实用玩法：让它真的参与工作流

我建议群组不要只做视觉，而是绑定 Claude Code 的任务流程。

### 方案 A：一个任务一个小队

用户输入：

> 帮我修复登录失败的问题

系统弹出一个任务卡：

```text
任务：修复登录失败
推荐小队：
- Planner：分析问题
- Coder：修改代码
- Tester：运行测试
- Reviewer：检查风险
```

用户点击“创建小队”，几个 Agent 自动走到会议桌。

流程可以是：

```text
会议桌讨论 → Planner 生成计划
Coder 回工位修改
Tester 去测试区运行测试
Reviewer 去 Review 区审查
最后大家回会议桌总结
```

这个就很有趣，而且有实际意义。

---

### 方案 B：群组协作模式

给小队几种模式：

| 模式 | 行为 |
|---|---|
| 讨论模式 | 多个 Agent 围在会议桌，轮流发气泡 |
| 执行模式 | 各自回工位做子任务 |
| Review 模式 | Reviewer 靠近 Coder 工位，查看 diff |
| Debug 模式 | 多个 Agent 聚集到日志屏幕前 |
| 等待用户模式 | 小队成员一起看向屏幕 / 举手 / 冒问号 |

比如用户选择“Debug 模式”，几个 Agent 会自动走到 Debug 角落，然后一个看日志、一个看代码、一个写笔记。

这比“形成群组”更有价值。

---

## 三、Agent 活灵活现：待机行为要分层设计

不要所有 Agent 都随机跳舞。那样一开始好玩，后面会烦。

我建议分成三类行为：

---

### 1. 状态型行为：反映真实工作状态

这是最重要的，既有趣又有信息量。

| Agent 状态 | 场景行为 |
|---|---|
| idle 空闲 | 玩手机、喝咖啡、伸懒腰、看窗外 |
| thinking 思考中 | 摸下巴、头上冒省略号、在白板前踱步 |
| coding 写代码 | 坐在电脑前敲键盘 |
| reading 读文件 | 拿文件夹 / 看书 / 翻页 |
| running command | 电脑屏幕闪烁、终端图标跳动 |
| waiting user input | 举手、冒问号、走到用户入口处 |
| error / failed | 头上冒红色感叹号、趴桌子、电脑冒烟 |
| success | 比 OK、跳一下、撒彩纸 |
| reviewing | 戴眼镜看文档、拿放大镜 |
| blocked | 原地转圈、挠头、走到帮助台 |

这些行为应该和真实 Claude Code 状态绑定，而不是纯随机。

---

### 2. 性格型行为：让不同 Agent 有个性

给每个 Agent 一个 personality profile。

比如：

```ts
type AgentPersonality = {
  energy: number;      // 活跃程度
  social: number;      // 是否喜欢找别人
  focus: number;       // 是否容易待在工位
  playful: number;     // 是否会跳舞/玩手机
  nervous: number;     // 出错时是否慌张
}
```

然后不同角色表现不一样：

| Agent 类型 | 待机行为 |
|---|---|
| Planner | 经常去白板前走动 |
| Coder | 大多坐工位，偶尔喝咖啡 |
| Reviewer | 经常巡视其他人 |
| Tester | 经常跑去测试区，看终端 |
| Researcher | 看书、查资料、翻文件 |
| Manager | 在办公室走来走去，靠近小队看状态 |

这样你会感觉他们真的“有职责”。

---

### 3. 社交型行为：增强办公室生命感

这类最有趣，但要克制。

可以设计一些随机 ambient events：

| 行为 | 触发条件 |
|---|---|
| 窃窃私语 | 两个 idle Agent 距离近 |
| 击掌 | 一个 Agent 成功完成任务，附近有人 |
| 围观 bug | 某 Agent 报错，附近 Agent 走过去看 |
| 跳舞 | 长时间空闲，低概率触发 |
| 喝咖啡 | idle 超过一定时间，走到咖啡机 |
| 玩手机 | idle 超过 30 秒 |
| 白板涂鸦 | Planner / Researcher 空闲 |
| 小憩 | 夜间或长时间无任务 |
| 吵架气泡 | 两个 Agent 对方案分歧时，冒出 ⚡ |
| 组内庆祝 | 小队任务完成 |

关键点：**这些行为最好跟上下文有关**。

比如不要无缘无故跳舞，而是：

- 任务完成后跳舞；
- 测试全绿后击掌；
- 出错后围观；
- 长时间等待用户时开始玩手机。

这样就不是装饰，而是场景反馈。

---

## 四、我建议你做一个“群组生命周期”

这是最核心的产品设计。

一个群组从创建到结束，可以有完整状态：

```text
创建小队
↓
会议讨论
↓
分工执行
↓
同步进度
↓
Review / 测试
↓
总结完成
↓
解散 / 归档
```

对应场景表现：

| 阶段 | 场景表现 |
|---|---|
| 创建小队 | 多个 Agent 走向会议桌 |
| 讨论 | 围桌站立，轮流冒气泡 |
| 分工 | 每个 Agent 走向不同区域 |
| 执行 | 各自在电脑、白板、测试区工作 |
| 同步 | 定时回会议桌碰头 |
| Review | Reviewer 走到 Coder 旁边 |
| 完成 | 聚集庆祝，生成总结卡片 |
| 解散 | 各自回工位或休息区 |

这套机制一旦做出来，你的平台就会从“像素皮肤”变成真正的 **任务可视化系统**。

## 六、家具也要变成功能节点

你现在能布置家具，但没有实用性，是因为家具只是 decoration。

可以把家具分成两类：

### 装饰家具

比如植物、沙发、地毯、墙画，只负责氛围。

### 功能家具

这些要绑定实际逻辑：

| 家具 | 功能 |
|---|---|
| 工位 | Agent 执行任务的位置 |
| 会议桌 | 群组讨论、计划生成 |
| 白板 | 展示 plan / todo / architecture |
| 看板 | 展示任务状态 |
| 终端屏幕 | 显示 command / logs |
| 测试台 | 显示测试进度 |
| Review 桌 | 显示 diff 和评论 |
| 咖啡机 | Agent idle 行为聚集点 |
| 沙发 | 休息、待机、离线状态 |
| 门口 | 新 Agent 入场 / 任务完成离场 |

这样用户会愿意布置办公室，因为布局会影响视觉工作流。

## 七、一个更有趣的设定：Agent 有“精力”和“注意力”

不一定真的影响模型执行，但可以影响 UI 表现。

例如：

```ts
energy: 0-100
focus: 0-100
mood: "focused" | "bored" | "excited" | "blocked"
```

表现方式：

| 状态 | 表现 |
|---|---|
| 精力高 | 走路快、动作积极 |
| 精力低 | 慢慢走、打哈欠 |
| 专注高 | 一直坐工位敲代码 |
| 无聊 | 玩手机、转椅子 |
| 卡住 | 挠头、看天花板、求助 |
| 兴奋 | 跳一下、头顶星星 |

这里不要真的让 Agent 因为“累了”而变笨，否则用户会烦。最好只是 UI 层氛围。

## 八、推荐你先做 MVP，不要一次做太多

我建议第一版只做这 6 个功能：

### MVP 1：Agent 状态动画

先把 Claude Code 状态映射到动作：

```text
idle → 玩手机 / 喝咖啡
thinking → 踱步
coding → 敲键盘
reading → 看文件
running → 终端闪烁
waiting → 举手
error → 冒红感叹号
success → 庆祝
```

这个最容易出效果。

---

### MVP 2：会议桌群组

做一个 `meetingZone`。

用户框选多个 Agent，点击：

```text
召集到会议桌
```

他们自动走过去，形成圆形站位，并显示群组气泡。

---

### MVP 3：小队面板

每个群组有：

```ts
groupId
name
goal
members
phase
currentSummary
```

点击群组能看到当前任务进度。

---

### MVP 4：自动同步

当小队执行任务时：

- 开始时聚到会议桌；
- 执行时各自回工位；
- 有错误时聚到 Debug 区；
- 完成时回会议桌总结。

这个会让场景“活起来”。

---

### MVP 5：家具功能化

先只做 4 个功能家具：

```text
会议桌
白板
工位
测试区
```

别一开始做太多。

---

### MVP 6：ambient idle 行为

空闲超过一定时间后：

```text
喝咖啡
玩手机
看书
窃窃私语
伸懒腰
跳舞
```

但设一个频率限制，比如每个 Agent 60 秒最多触发一次，避免太吵。

## 九、数据结构可以这样设计

你可以在前端维护一个 world state：

```ts
type AgentState =
  | "idle"
  | "thinking"
  | "reading"
  | "coding"
  | "running"
  | "waiting_user"
  | "blocked"
  | "error"
  | "success"
  | "reviewing"
  | "testing"
  | "meeting";

type Agent = {
  id: string;
  name: string;
  role: "planner" | "coder" | "tester" | "reviewer" | "researcher";
  position: { x: number; y: number };
  target?: { x: number; y: number };
  state: AgentState;
  groupId?: string;
  currentTask?: string;
  personality: {
    energy: number;
    social: number;
    focus: number;
    playful: number;
  };
};

type AgentGroup = {
  id: string;
  name: string;
  goal: string;
  members: string[];
  phase: "forming" | "meeting" | "working" | "debugging" | "reviewing" | "done";
  zoneId?: string;
  summary?: string;
};

type Zone = {
  id: string;
  type: "desk" | "meeting_table" | "whiteboard" | "debug_screen" | "test_area" | "coffee";
  position: { x: number; y: number };
  capacity: number;
};
```

这样后面扩展会很舒服。

## 十、最值得做的几个“趣味事件”

我觉得这些最有性价比：

### 1. Bug 围观

当某个 Agent 失败：

```text
Coder 报错
↓
Reviewer 和 Tester 自动走过来
↓
三个人头上冒出：
Coder: "这里炸了..."
Tester: "我来复现"
Reviewer: "先看 diff"
```

非常有趣，而且符合真实开发。

---

### 2. 测试全绿庆祝

测试通过后：

```text
Tester 跳一下
Coder 和 Reviewer 击掌
白板出现 ✅ All tests passed
```

这个反馈会很爽。

---

### 3. 等待用户输入

当 Claude Code 需要确认：

```text
Agent 走到屏幕前
头上冒问号
小气泡：需要你批准命令
```

比现在纯文字提示更直观。

---

### 4. 小队晨会

任务开始时：

```text
所有成员到会议桌
Planner 在白板写 plan
Coder 点头
Tester 举手
Reviewer 翻文件
```

这会让多 Agent 协作更有仪式感。

---

### 5. 空闲社交

两个 idle Agent 靠近时：

```text
Agent A: "今天的 bug 有点凶"
Agent B: "但测试终于绿了"
```

气泡内容可以从固定模板生成，不需要真的调用模型，省成本。

## 我最推荐的产品方向

你这个平台不要定位成“Claude Code 换皮 UI”，而是定位成：

> **一个可视化的多 Agent 开发工作室。**

它的价值应该是：

```text
用户不是在看一堆终端输出，
而是在指挥一个小团队完成任务。
```

所以最关键的三个设计点是：

1. **Agent 的位置表达职责**：工位、白板、测试区、Review 区；
2. **Agent 的动作表达状态**：写代码、卡住、等待、成功；
3. **群组表达协作关系**：谁和谁在解决同一个问题。

先别急着做太多“玩手机、跳舞”。那些是锦上添花。真正让它变好玩的，是用户一眼能看到：

```text
谁在干活？
谁卡住了？
谁在等我？
哪个小队快完成了？
哪里出 bug 了？
```

当这个信息流打通以后，再加待机动画，整个系统就会又实用又有生命感。
