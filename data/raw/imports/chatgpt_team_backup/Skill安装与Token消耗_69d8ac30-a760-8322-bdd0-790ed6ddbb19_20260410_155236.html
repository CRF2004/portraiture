结论先说清楚：“安装很多 skill 但不使用”，通常不会直接消耗 token。真正决定 token 消耗的是运行时是否被加载/触发/注入上下文。

但这里有几个关键细节，容易被误解，我拆开讲。

---

## 1. Skill “安装”本身不消耗 token
无论是 Claude Code 还是类似 MCP/skills 体系：

- skill 只是本地配置 / 文件 / 注册表
- 不执行、不读取 → 不会产生任何 API token 消耗

所以：
> 装 100 个 skill ≠ 自动耗 token

---

## 2. 什么时候会“间接耗 token”
真正可能增加 token 消耗的是下面三种情况：

### A. 启动时自动加载 skill 内容
如果系统设计是：
- 启动 Claude Code 时
- 把所有 skill description / schema / prompt
- 一次性塞进 context

那么：

👉 skill 越多 → system prompt 越长 → 每次请求 token 增加

但注意：
- 这是“一次性上下文成本”
- 不是持续消耗

---

### B. MCP / skill registry 被注入上下文
有些实现会：

- 把所有 tool / skill 列表注入模型
- 或动态生成 tool schema

这会导致：

👉 tool 数量越多 → 每次 request token baseline 更高

---

### C. skill 被候选召回（tool selection）
更高级的 agent 框架可能会：

- 每次推理前把“可用 skills”一起放进 prompt
- 让模型决定用哪个

这时：

👉 skill 越多 → prompt 越长 → token 上升

---

## 3. 不使用 skill ≠ 不影响 token（关键点）
你要区分两个概念：

| 行为 | 是否消耗 token |
|------|------|
| skill 安装 | ❌ 不消耗 |
| skill 未加载 | ❌ 不消耗 |
| skill 列表被注入 prompt | ⚠️ 消耗（固定开销） |
| skill 被调用 | ✅ 消耗（额外 tool call + output） |

---

## 4. 实际工程结论（非常重要）
在 Claude Code / MCP 实践里通常是：

### ✔ 小规模 skill（<20）
- 基本无影响
- 可以全部常驻

### ⚠ 中规模（20–100）
- 可能增加 system prompt token
- 但通常仍可接受

### ❌ 大规模（100+）
如果设计不好：
- tool/schema injection 会明显拖 token
- 甚至影响 reasoning quality（注意力稀释）

---

## 5. 优化建议（更工程化）
如果你担心 token 或性能：

### 方案 1：lazy loading skills（推荐）
- 只注册 metadata
- 真正 schema 按需加载

### 方案 2：skill grouping
例如：

medical_skills/
devops_skills/
research_skills/


按 session 或任务加载

### 方案 3：tool router（类似 MCP gateway）
- 先让 router 决定 skill 子集
- 再注入模型

---

## 6. 一句话总结
> skill 不用不会耗 token，但“被加载进 prompt 的 skill 描述”会消耗 token，规模越大影响越明显。
