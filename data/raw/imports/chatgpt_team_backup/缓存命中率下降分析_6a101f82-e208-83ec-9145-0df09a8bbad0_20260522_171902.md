你说“差了 600 万 token”，如果是按成本感受或者按平时 96%～97% 命中率预期来算，体感接近是合理的；但按截图严格折算，**缓存额外损失大概是 320 万～374 万 input token**，不是完整 600 万。

最可能的原因不是模型输出问题，而是**前缀缓存被打断了**。DeepSeek 这类缓存一般对“前面完全相同的一段 token”敏感，只要靠前位置变了，后面一大段都可能不命中。

重点排查这几个：

1. **system prompt / tools schema / RAG 上下文今天变了**  
   比如工具列表顺序、JSON schema、函数描述、知识库片段顺序，只要变动在前面，缓存命中会大跌。

2. **把时间戳、请求 ID、用户 ID、随机 trace 放在了 prompt 前面**  
   这很常见。每天日期、会话 ID、动态 metadata 如果放在 system 或开头，会让本来能复用的长前缀全部失效。  
   正确做法是：稳定内容放最前，动态内容尽量放最后。

3. **今天请求更分散，复用前缀少了**  
   比如昨天大量请求来自同一个工作流，今天来自多个项目、多个 agent、多个 prompt 模板，命中率自然会掉。

4. **agent 动态注入 memory / 文件 / 检索结果的位置变了**  
   如果 RAG 结果被塞在系统提示词附近，且每次不同，会严重破坏缓存。最好把固定模板放前面，检索结果靠后。

5. **模型名或路由变了**  
   例如 `deepseek-v4-pro` 实际后端版本、区域、供应商路由、fallback 模型发生变化，也可能导致缓存不可复用。这个需要看服务商后台日志确认。

我建议你马上做一个简单定位：抽今天和昨天各 20 条请求，把**前 2000～8000 token 的 prompt 做 hash**。如果 hash 今天每条都不一样，而昨天大量相同，问题就在 prompt 组装；如果 hash 基本一样但仍不命中，才更像是供应商缓存侧、模型版本或路由问题。

最该先查的是：**今天有没有新增日期、trace、session、memory、tools schema 或 RAG 内容被放到了 prompt 开头。** 这个最容易造成你截图里这种从 95%+ 掉到 88% 的情况。
